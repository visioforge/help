## Overview

This guide demonstrates how to capture video from ONVIF IP cameras while applying various postprocessing effects before encoding to MP4. Unlike pass-through recording which preserves the original stream, postprocessing requires decoding the video, applying transformations, and re-encoding.

This approach is useful when you need to: - Resize or crop video - Apply brightness, contrast, or color corrections - Add watermarks or logos - Blur faces for privacy - Apply artistic effects or filters - Combine multiple processing steps

## When to Use Postprocessing

**Use postprocessing when:** - You need to resize video (e.g., from 4K to 1080p) - You want to apply video effects (brightness, contrast, etc.) - You need to add overlays or watermarks - Privacy requirements mandate face blurring - You're combining multiple camera feeds - You need to apply AI/CV algorithms

**Use pass-through (no postprocessing) when:** - You want to preserve original video quality - You need to minimize CPU usage - Storage space is not a concern - Recording duration is long (hours/days)

For pass-through recording, see [Save RTSP Stream without Re-encoding](../rtsp-save-original-stream/).

## Basic Setup: ONVIF Discovery and Connection

First, discover and connect to your ONVIF camera:

```
using VisioForge.Core.ONVIFDiscovery;
using VisioForge.Core.ONVIFX;

// Discover ONVIF cameras
var discovery = new Discovery();
var cts = new CancellationTokenSource();
string cameraUrl = null;

await discovery.Discover(5, (device) =>
{
    if (device.XAdresses?.Any() == true)
    {
        cameraUrl = device.XAdresses.FirstOrDefault();
        Console.WriteLine($"Found camera: {cameraUrl}");
    }
}, cts.Token);

if (string.IsNullOrEmpty(cameraUrl))
{
    Console.WriteLine("No ONVIF cameras found");
    return;
}

// Connect to camera
var onvifClient = new ONVIFClientX();
bool connected = await onvifClient.ConnectAsync(cameraUrl, "admin", "password");

if (!connected)
{
    Console.WriteLine("Failed to connect to camera");
    return;
}

// Get RTSP stream URL
var profiles = await onvifClient.GetProfilesAsync();
var streamUri = await onvifClient.GetStreamUriAsync(profiles[0]);
string rtspUrl = streamUri.Uri;

Console.WriteLine($"RTSP URL: {rtspUrl}");
```

## Example 1: Resize Video

Resize video from ONVIF camera before saving to MP4. The Media Blocks API takes settings objects, not fluent properties — `RTSPSourceBlock` is constructed from an `RTSPSourceSettings`, the encoder from its settings object, the MP4 sink hands out input pads via `CreateNewInput(...)`, and links are declared on the pipeline.

```
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.VideoProcessing;
using VisioForge.Core.MediaBlocks.VideoEncoders;
using VisioForge.Core.MediaBlocks.AudioEncoders;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.Types.X.Sources;
using VisioForge.Core.Types;

// Create pipeline
var pipeline = new MediaBlocksPipeline();

// RTSP source from ONVIF camera. Credentials and latency live on the settings
// object; use the async factory so the settings discover codec info up front.
var rtspSettings = await RTSPSourceSettings.CreateAsync(
    new Uri(rtspUrl), "admin", "password", audioEnabled: true);
var rtspSource = new RTSPSourceBlock(rtspSettings);

// Video resize block — downscale to 1280x720. The (width, height) ctor is a
// shortcut for `new VideoResizeBlock(new ResizeVideoEffect(w, h))`.
var videoResize = new VideoResizeBlock(1280, 720);

// H.264 encoder. Pick a concrete settings class — Bitrate is in Kbit/s (2000 = 2 Mbps).
// OpenH264EncoderSettings works on every platform; swap to NVENC / QSV / AMF / MFH264 for GPU acceleration.
var h264Settings = new OpenH264EncoderSettings { Bitrate = 2000 };
var h264Encoder = new H264EncoderBlock(h264Settings);

// AAC audio encoder (Bitrate is in Kbit/s — 128 = 128 kbps).
var aacEncoder = new AACEncoderBlock(new AVENCAACEncoderSettings { Bitrate = 128 });

// MP4 sink — file-path ctor is the shortest path to a valid MP4 writer.
var mp4Sink = new MP4SinkBlock("output_resized.mp4");

// Add every block to the pipeline before wiring links
pipeline.AddBlock(rtspSource);
pipeline.AddBlock(videoResize);
pipeline.AddBlock(h264Encoder);
pipeline.AddBlock(aacEncoder);
pipeline.AddBlock(mp4Sink);

// Wire the video path (RTSP video → resize → H.264 → MP4 sink video pad)
pipeline.Connect(rtspSource.VideoOutput, videoResize.Input);
pipeline.Connect(videoResize.Output, h264Encoder.Input);
pipeline.Connect(h264Encoder.Output, mp4Sink.CreateNewInput(MediaBlockPadMediaType.Video));

// Wire the audio path (RTSP audio → AAC → MP4 sink audio pad)
// AudioOutput is null when the source was created with audioEnabled: false or the camera info shows no audio; in compatibility mode with audio on it exists even for a camera without audio.
if (rtspSource.AudioOutput != null)
{
    pipeline.Connect(rtspSource.AudioOutput, aacEncoder.Input);
    pipeline.Connect(aacEncoder.Output, mp4Sink.CreateNewInput(MediaBlockPadMediaType.Audio));
}

// Start recording
await pipeline.StartAsync();

Console.WriteLine("Recording with resize... Press Enter to stop.");
Console.ReadLine();

// Stop and cleanup
await pipeline.StopAsync();
await pipeline.DisposeAsync();

Console.WriteLine("Recording complete: output_resized.mp4");
```

## Example 2: Apply Video Effects

Apply brightness, contrast, hue, and saturation adjustments. Video-processing blocks take a settings object in the ctor; the settings carry the knobs.

```
using VisioForge.Core.MediaBlocks.VideoProcessing;
using VisioForge.Core.Types.X.VideoEffects;

// Create pipeline
var pipeline = new MediaBlocksPipeline();

// RTSP source
var rtspSettings = await RTSPSourceSettings.CreateAsync(
    new Uri(rtspUrl), "admin", "password", audioEnabled: true);
var rtspSource = new RTSPSourceBlock(rtspSettings);

// Video-balance block — knobs live on the settings object.
// Brightness: -1.0..1.0 (0.2 = slightly brighter)
// Contrast:    0.0..2.0 (1.15 = +15% contrast)
// Saturation:  0.0..2.0 (1.3  = +30% saturation)
// Hue:        -1.0..1.0 (0.0  = no shift)
var balanceSettings = new VideoBalanceVideoEffect
{
    Brightness = 0.2,
    Contrast   = 1.15,
    Saturation = 1.3,
    Hue        = 0.0,
};
var videoBalance = new VideoBalanceBlock(balanceSettings);

// Color-effects block takes a preset directly in the ctor
var colorEffects = new ColorEffectsBlock(ColorEffectsPreset.Sepia);

// H.264 encoder (3 Mbps)
var h264Settings = new OpenH264EncoderSettings { Bitrate = 3000 };
var h264Encoder = new H264EncoderBlock(h264Settings);

// AAC audio
var aacEncoder = new AACEncoderBlock(new AVENCAACEncoderSettings { Bitrate = 128 });

// MP4 output
var mp4Sink = new MP4SinkBlock("output_enhanced.mp4");

// Add everything to the pipeline, then wire
pipeline.AddBlock(rtspSource);
pipeline.AddBlock(videoBalance);
pipeline.AddBlock(colorEffects);
pipeline.AddBlock(h264Encoder);
pipeline.AddBlock(aacEncoder);
pipeline.AddBlock(mp4Sink);

// Video chain: RTSP → balance → color-effects → H.264 → MP4
pipeline.Connect(rtspSource.VideoOutput, videoBalance.Input);
pipeline.Connect(videoBalance.Output, colorEffects.Input);
pipeline.Connect(colorEffects.Output, h264Encoder.Input);
pipeline.Connect(h264Encoder.Output, mp4Sink.CreateNewInput(MediaBlockPadMediaType.Video));

// Audio chain
// AudioOutput is null when the source was created with audioEnabled: false or the camera info shows no audio; in compatibility mode with audio on it exists even for a camera without audio.
if (rtspSource.AudioOutput != null)
{
    pipeline.Connect(rtspSource.AudioOutput, aacEncoder.Input);
    pipeline.Connect(aacEncoder.Output, mp4Sink.CreateNewInput(MediaBlockPadMediaType.Audio));
}

// Start
await pipeline.StartAsync();

Console.WriteLine("Recording with enhancements...");
await Task.Delay(TimeSpan.FromMinutes(5)); // Record for 5 minutes

await pipeline.StopAsync();
await pipeline.DisposeAsync();
```

using VisioForge.Core.MediaBlocks.OpenCV;

## Performance Considerations

1. **CPU Usage**: Video processing is CPU-intensive. Each effect adds overhead:
2. Simple resize: ~10-20% CPU per stream
3. Color correction: ~5-15% CPU
4. Face detection: ~30-50% CPU (depends on resolution)
5. Multiple effects: Additive CPU usage
6. **GPU Acceleration**: Use hardware-accelerated encoders when available. `H264EncoderBlock.GetDefaultSettings()` already prefers NVENC / QSV / AMF when the platform supports it, but you can force a specific backend:

```
// NVIDIA NVENC H.264 encoder (Bitrate in Kbit/s — 4000 = 4 Mbps)
var nvencSettings = new NVENCH264EncoderSettings { Bitrate = 4000 };
var h264Encoder   = new H264EncoderBlock(nvencSettings);
```

1. **Error handling**: Subscribe to `OnError` to learn about pipeline failures:

```
pipeline.OnError += (sender, e) =>
{
    Console.WriteLine($"Pipeline error: {e.Message}");
};
```

1. **Encoding Settings Balance**:
2. **Quality**: Higher bitrate, slower preset = better quality, more CPU
3. **Performance**: Lower bitrate, faster preset = lower quality, less CPU
4. **File Size**: Bitrate directly affects file size

## Best Practices

1. **Test Performance First**:
2. Start with simple pipeline
3. Add effects one at a time
4. Monitor CPU/memory usage
5. Adjust settings based on hardware
6. **Choose Appropriate Bitrates** (all values in Kbit/s):
7. 720p: 1000-2000
8. 1080p: 2000-4000
9. 4K: 8000-15000
10. **Dispose Resources**:

```
try
{
    await pipeline.StartAsync();
    // ... recording ...
}
finally
{
    await pipeline.StopAsync();
    await pipeline.DisposeAsync();
    onvifClient?.Dispose();
}
```

1. **Observe pipeline lifecycle events**:

```
pipeline.OnStart  += (s, e) => Console.WriteLine("Pipeline started");
pipeline.OnStop   += (s, e) => Console.WriteLine("Pipeline stopped");
pipeline.OnPause  += (s, e) => Console.WriteLine("Pipeline paused");
pipeline.OnResume += (s, e) => Console.WriteLine("Pipeline resumed");
```

## Troubleshooting

**High CPU Usage:** - Reduce video resolution - Lower encoder preset (faster encoding) - Remove unnecessary effects - Use GPU acceleration if available

**Dropped Frames:** - Check if CPU is bottlenecked - Reduce frame rate - Lower bitrate - Simplify processing pipeline

**Poor Video Quality:** - Increase bitrate - Use slower encoder preset - Check source video quality - Verify network bandwidth for RTSP

**Memory Leaks:** - Ensure proper disposal of blocks - Check for circular references - Monitor long-running recordings

**Effects Not Applied:** - Verify block connections via `pipeline.Connect(outPad, inPad)` - Check effect parameters are valid - Ensure every block is registered via `pipeline.AddBlock(...)` before `StartAsync` - Review pipeline order (effects chain)

## Overview

A Media Blocks pipeline is normally built in code: you construct blocks, connect their pads, and start the pipeline. The persistence layer lets you do the same thing with a **document** — an ordinary JSON file that names the blocks, their settings and their connections. That document can be written by your application, edited by hand, shipped as a preset, or produced by a visual editor.

Three types do the work, and each has a single responsibility:

| Type | What it does |
| --- | --- |
| `MediaBlocksPipelineJsonSerializer` | JSON text ⇄ `MediaBlocksPipelineDocument` |
| `MediaBlocksPipelineValidator` | checks a document *before* anything is built |
| `MediaBlocksPipelineMaterializer` | document → live `MediaBlocksPipeline` |

The reverse direction — live pipeline → document — is `MediaBlocksPipelineSnapshot`, reached through `MediaBlocksPipeline.ToDocument()`.

```
flowchart LR
    JSON[JSON file] -->|Load| Document[MediaBlocksPipelineDocument]
    Document -->|Validate| Diagnostics[Diagnostics]
    Document -->|Materialize| Pipeline[MediaBlocksPipeline]
    Pipeline -->|ToDocument| Document
    Document -->|Serialize| JSON
```

## The document model

`MediaBlocksPipelineDocument` is a plain DTO tree:

- `SchemaVersion` — the document format version. Older versions are migrated on load.
- `Pipeline` — `Id`, `Name` and optional pipeline-level settings.
- `Blocks` — a `MediaBlockDocument` each: `Id` (a `Guid`), `Type` (the `MediaBlockType` value), `TypeName`, `Name`, and a `Settings` payload.
- `Connections` — a `MediaBlockConnectionDocument` each, with a `From` and a `To` `MediaBlockPadReference`.

A pad reference is a block id plus a **pad id**, and the pad id follows one convention:

| Pad id | Meaning |
| --- | --- |
| `input` / `output` | the block's main pad |
| `input:N` / `output:N` | element *N* of the block's `Inputs` / `Outputs` list |

The indexed form is the one to prefer when you generate documents: it addresses any block, while the unindexed form needs a main pad that not every block has. For a muxing sink such as `MP4SinkBlock`, `input:0` and `input:1` are the video and audio streams.

Muxing sinks create their inputs while the document loads. For those, the `To` reference may also carry a `mediaType` (`Video`, `Audio`, …) — the pipeline snapshot writes it — and the input is created with that type; without it, the input takes the type of the connected output pad. A sink that has no track for an input's type — an `Auto` input from a tee or a parser on an MP4 sink, for one — fails the pipeline start with an error; an MPEG-TS sink outside split mode takes an `Auto` input.

A minimal document:

```
{
  "schemaVersion": 1,
  "pipeline": { "id": "6f0d1b6e-1f7a-4f1e-9a1a-0a0f3d5f7a11", "name": "Player" },
  "blocks": [
    {
      "id": "10000000-0000-4000-8000-000000000001",
      "type": 3,
      "typeName": "UniversalSource",
      "name": "Media File",
      "settings": { "uri": "clips/sample.mp4", "renderVideo": true, "renderAudio": true }
    },
    {
      "id": "10000000-0000-4000-8000-000000000002",
      "type": 21,
      "typeName": "VideoRenderer",
      "name": "Preview"
    }
  ],
  "connections": [
    {
      "from": { "blockId": "10000000-0000-4000-8000-000000000001", "padId": "output:0" },
      "to":   { "blockId": "10000000-0000-4000-8000-000000000002", "padId": "input" }
    }
  ]
}
```

## Building a pipeline from JSON

The shortest path replaces an existing pipeline's contents:

```
var pipeline = new MediaBlocksPipeline();

var result = await pipeline.LoadJsonAsync(
    File.ReadAllText("player.json"),
    resolver: null,
    baseDirectory: Path.GetDirectoryName(Path.GetFullPath("player.json")));

if (!result.Success)
{
    foreach (var diagnostic in result.Diagnostics)
    {
        Console.WriteLine(diagnostic);
    }

    return;
}

await pipeline.StartAsync();
```

`LoadJsonAsync` requires the pipeline to be stopped, and it never leaves a half-built graph behind: if materialization fails partway, the pipeline is cleared.

To build a pipeline without owning one first, use the materializer directly. It returns the pipeline *and* the mapping from document ids to live blocks, which is what you need to reach a block afterwards:

```
var loaded = MediaBlocksPipelineJsonSerializer.Load(json);
var result = MediaBlocksPipelineMaterializer.Materialize(loaded.Document, resolver: null, baseDirectory: folder);

if (result.Success)
{
    var overlay = (TextOverlayBlock)result.Blocks[captionId];
    overlay.Settings.Text = "Live";
}
```

### Network sources are probed when the pipeline starts

A document carries a source's endpoint, never its media information: restoring one contacts nothing. Two sources need that information before they can be built — `RTSPRAWSourceBlock` picks its depayloader and parser from the stream layout, and the desktop `NDISourceBlock` creates its converters from the stream counts — so `StartAsync` probes them for you, once, before the graph is built. The camera or sender has to be reachable at that moment; if it is not, `StartAsync` returns `false` and logs which source could not be read.

The synchronous `Start` has nowhere to await a probe and does not do this, and neither do the `VideoCaptureCoreX` and `MediaPlayerCoreX` engines, which build their graph through it. Restore a document whose pipeline you intend to start that way by replacing those settings with ones built through `RTSPRAWSourceSettings.CreateAsync` / `NDISourceSettings.CreateAsync` after materialization.

### Audio devices are matched back to this machine

A document stores what identifies an audio device — its name, the API it belongs to, the endpoint path where the platform publishes one, and, on macOS, the stable CoreAudio `unique-id` — and never the enumerator's live handle, which means nothing outside the process that made it. Materialization matches that identity against the devices this machine has now and hands the block a live device again. That is also why a restored pipeline opens the right endpoint: the numeric CoreAudio id and the WASAPI device path are reassigned between runs, and the match re-reads the current ones.

If the device is gone, the pipeline still builds — on another device of the same API, reported as an `MBS063` warning naming both. If the machine has no device of that API at all, the block keeps the document's identity and materialization reports `MBS064`; the block will not open anything.

Matching enumerates devices, which on a cold process starts a GStreamer device monitor and can take seconds, so call `Materialize` off the UI thread — or enumerate once beforehand. Inputs and outputs are cached separately: `AudioSourcesAsync` warms capture devices, `AudioOutputsAsync` warms renderers, and on Apple platforms the asynchronous capture call is also the one that asks for microphone permission. The synchronous match inside `Materialize` does neither.

## Validating before you build

`Validate` answers the same questions materialization would, without constructing anything — so a UI can show a document's problems while the user edits it:

```
var diagnostics = MediaBlocksPipelineValidator.Validate(
    document,
    resolver: null,
    baseDirectory: folder);

var errors = diagnostics.Where(d => d.Severity == MediaBlocksDiagnosticSeverity.Error).ToList();
```

It checks the document's structure, that every block type is known to this build, that each block has a construction path, that pad references parse and point at pads the block actually has, that no feedback cycle exists, and — when you pass a `baseDirectory` — that the files a source reads are present.

Pass `baseDirectory: null` to skip the file-system checks entirely; that is the default, and it keeps the behaviour of a document you validate before its assets are in place.

## Capturing a live pipeline

`ToDocument()` walks the live graph and produces a document. It is safe while the pipeline is running — the block list is taken under the pipeline's own lock and nothing is changed — which makes it the save-during-Run path:

```
var snapshot = pipeline.ToDocument();

if (!snapshot.Complete)
{
    foreach (var diagnostic in snapshot.Diagnostics)
    {
        Console.WriteLine(diagnostic);
    }
}

await MediaBlocksPipelineJsonSerializer.SaveFileAsync(snapshot.Document, "captured.json");
```

`ToJson()` and `SaveJsonAsync(path)` are the one-line forms; they send the diagnostics to the SDK log instead of returning them.

The graph is captured exactly; the settings are not always

A block's identity, type and connections can be read from any block, so the **shape** of a pipeline always round-trips. Its **configuration** can only be read from blocks that expose their settings — 153 of this SDK's 404 block types do. For the rest there is nothing to read, and rather than write a document that looks complete and rebuilds the block on its defaults, the snapshot reports an `MBS060` diagnostic and leaves that block's `settings` empty.

Check `MediaBlocksPipelineSnapshotResult.Complete` before treating a snapshot as a faithful copy. A pipeline that was itself built from a document round-trips fully, because materialization stamps the document's block ids onto the blocks it creates.

## Relative asset paths

Settings that name a file may be relative to the document. Pass the document's folder as `baseDirectory`, and both validation and materialization resolve them against it:

```
var folder = Path.GetDirectoryName(Path.GetFullPath(documentPath));
var result = MediaBlocksPipelineMaterializer.Materialize(document, resolver: null, baseDirectory: folder);
```

The rewriting covers `Uri`-typed settings and string settings named `*Path`, `*File`, `Filename` or `*Location`. Values that name an endpoint rather than a file are left alone — anything with a scheme (`rtsp://`, `srt://:8888/`), an IPv4 literal, or a first segment that reads as a host name (`cam.local/stream.m3u8`). A folder whose name reads like a host is ambiguous, and the validator says so with an `MBS057` warning; prefix such a value with `./` to force the folder reading.

## Diagnostics

Every entry point returns `MediaBlocksDiagnostic` values rather than throwing, so a host can show the whole list at once. Each carries a `Severity`, a `Code`, a `Message` and the `BlockId` it belongs to.

| Code | Meaning |
| --- | --- |
| `MBS031` | unknown block type — this build's catalog has no such block |
| `MBS032` | the block has no construction path |
| `MBS040` | the block could not be constructed |
| `MBS048` / `MBS054` | a pad reference could not be resolved, or a pad is used twice |
| `MBS049` | the settings have no default constructor and the document carries no usable payload |
| `MBS050` | the settings payload could not be deserialized |
| `MBS055` | a file a source reads is not there |
| `MBS056` | a `resources` entry could not be applied |
| `MBS057` | a value that reads as a network endpoint was left as written |
| `MBS060` | a block did not expose its settings to a snapshot |
| `MBS061` | a block could not be named in a snapshot |
| `MBS062` | a connection could not be expressed in a snapshot |
| `MBS063` | the audio device a block names is gone, and another device of the same API is used instead |
| `MBS064` | the audio device a block names could not be attached at all — nothing of that API is present, or the lookup failed |

## Overview

Pre-event recording (also known as circular buffer recording or retrospective recording) is a key surveillance feature that continuously buffers the last N seconds of encoded video and audio in memory. When an event triggers — such as motion detection, an alarm signal, or an API call — the buffered pre-event footage is written to a file along with post-event recording. This creates complete event clips that include footage from before the trigger, so you never miss critical moments.

This guide demonstrates how to record IP camera streams and webcam video with pre-event buffering using the VisioForge Media Blocks SDK for .NET. It covers RTSP camera capture, motion detection triggered recording, and saving event clips to MP4 or MPEG-TS files.

## Video Tutorial: Motion-Triggered Recording in C# WPF

The tutorial walks through the Pre-Event Recording WPF demo: an RTSP IP camera goes through motion detection to a preview and to `PreEventRecordingBlock`, which keeps the last seconds of encoded video and audio in memory. Motion starts the recording, so each saved file begins before the motion did. The video also covers extending and stopping a recording, and MPEG-TS files that stay playable after a power loss.

### The short version

A console app in a few lines of C#: it buffers the video of an RTSP camera in memory and, when you press Enter, saves up to 10 seconds from before that moment, starting at a key frame, and five more seconds of live video to an MP4 file. The login and password are written in its code: replace `admin` and `password` with your camera's.

```
using System.IO;
using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.VideoEncoders;
using VisioForge.Core.Types.X.PreEventRecording;
using VisioForge.Core.Types.X.Sources;

await VisioForgeX.InitSDKAsync();
await using var p = new MediaBlocksPipeline();
p.OnError += (_, e) =>
    Console.WriteLine(e.Message);
var cam = new RTSPSourceBlock(
    await RTSPSourceSettings.CreateAsync(
        new Uri(args[0]), "admin", "password",
        audioEnabled: false));
var h264 = new H264EncoderBlock();
var settings = new PreEventRecordingSettings
{
    PreEventDuration = TimeSpan.FromSeconds(10),
    PostEventDuration = TimeSpan.FromSeconds(5)
};
var pre = new PreEventRecordingBlock(settings)
    { AudioEnabled = false };
var saved = new TaskCompletionSource<string>(
    TaskCreationOptions
        .RunContinuationsAsynchronously);
pre.OnRecordingStopped += (_, e) =>
    saved.TrySetResult(e.Filename);
p.Connect(cam.VideoOutput, h264.Input);
p.Connect(h264.Output, pre.VideoInput);
if (!await p.StartAsync()) return;
var file = Path.GetFullPath("event.mp4");
do
{
    Console.WriteLine("Enter: the event");
    if (Console.ReadLine() is null) return;
    pre.TriggerRecording(file);
}
while (pre.State ==
    PreEventRecordingState.Buffering);
Console.WriteLine(await saved.Task);
await p.StopAsync();

## Core Features

- **Continuous buffering**: Encoded frames are stored in a managed circular buffer with configurable duration
- **Keyframe-aware**: Recording always starts from the earliest video keyframe (I-frame) in the buffer for proper playback
- **Event-triggered output**: Files are created only when events occur — no continuous disk writes
- **Automatic post-event recording**: Configurable post-event duration with auto-stop
- **Extend on re-trigger**: If triggered again during recording, the post-event timer resets without creating a new file
- **Multiple container formats**: MP4 (default), MPEG-TS (crash-safe), and MKV
- **Thread-safe**: All buffer and state operations are synchronized for multi-threaded access

## How It Works

The `PreEventRecordingBlock` sits at the end of an encoding pipeline and operates in two modes:

**Buffering mode** (normal operation):

1. Encoded video and audio frames flow into the block from upstream encoders
2. Frames are stored in a time-limited circular buffer (ring buffer) in memory
3. When the buffer exceeds the configured `PreEventDuration`, the oldest frames are evicted
4. No disk I/O occurs during buffering

**Recording mode** (after trigger):

1. `TriggerRecording("event_001.mp4")` is called
2. The block finds the earliest video keyframe in the buffer
3. A dynamic output pipeline is created: AppSrc → Muxer → FileSink
4. All buffered frames from the keyframe onward are flushed to the file
5. Live frames continue flowing to the file in real-time
6. After the `PostEventDuration` timer expires, recording stops automatically
7. The output pipeline is torn down and the block returns to buffering mode

```
graph TD;
    A[IP Camera RTSP Source] --> B[Video Encoder H.264];
    A --> C[Audio Encoder AAC];
    B --> D[PreEventRecordingBlock];
    C --> D;
    D --> E{Trigger?};
    E -- No --> F[Ring Buffer in Memory];
    F --> E;
    E -- Yes --> G[Flush Buffer + Record to File];
    G --> H[Post-Event Timer];
    H --> F;
```

## Code Sample: WPF Application with Camera and Motion Detection

The following C# code is based on the [Pre-Event Recording WPF demo](https://github.com/visioforge/.Net-SDK-s-samples). It demonstrates a complete pipeline with a camera source, motion detection for automatic triggering, video preview, and pre-event recording to MP4 files.

Demo Sample

For a complete working project with XAML and all dependencies, see the [Pre-Event Recording Media Blocks Demo](https://github.com/visioforge/.Net-SDK-s-samples/tree/master/Media%20Blocks%20SDK/WPF/CSharp/PreEventRecording).

```
using System;
using System.Diagnostics;
using System.IO;
using System.Linq;
using System.Windows;

using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.AudioEncoders;
using VisioForge.Core.MediaBlocks.AudioRendering;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.Special;
using VisioForge.Core.MediaBlocks.VideoEncoders;
using VisioForge.Core.MediaBlocks.VideoProcessing;
using VisioForge.Core.MediaBlocks.VideoRendering;
using VisioForge.Core.Types;
using VisioForge.Core.Types.Events;
using VisioForge.Core.Types.X.PreEventRecording;
using VisioForge.Core.Types.X.Sources;
using VisioForge.Core.Types.X.VideoEffects;

public partial class MainWindow : Window, IDisposable
{
    // Pipeline blocks
    private MediaBlocksPipeline _pipeline;
    private MediaBlock _videoSource;
    private MediaBlock _audioSource;
    private TeeBlock _videoTee;
    private TeeBlock _audioTee;
    private VideoRendererBlock _videoRenderer;
    private AudioRendererBlock _audioRenderer;
    private H264EncoderBlock _h264Encoder;
    private AACEncoderBlock _aacEncoder;
    private PreEventRecordingBlock _preEventBlock;
    private MotionDetectionBlock _motionDetector;
    private MotionDetectionBlockSettings _motionSettings;

    private string _outputFolder;
    private System.Timers.Timer _statusTimer;

    private async void BtStart_Click(object sender, RoutedEventArgs e)
    {
        // Ensure output folder exists
        _outputFolder = Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.MyVideos),
            "PreEventRecording");
        Directory.CreateDirectory(_outputFolder);

        bool audioEnabled = true;

        // Create pipeline
        _pipeline = new MediaBlocksPipeline();
        _pipeline.OnError += (s, args) => Log($"[Error] {args.Message}");

        // Video source (camera device)
        var device = (await DeviceEnumerator.Shared.VideoSourcesAsync()).FirstOrDefault();
        var videoSourceSettings = new VideoCaptureDeviceSourceSettings(device);
        _videoSource = new SystemVideoSourceBlock(videoSourceSettings);

        // Motion detection (frame differencing, no OpenCV required)
        _motionSettings = new MotionDetectionBlockSettings
        {
            MotionThreshold = 5,
            CompareGreyscale = true,
            GridWidth = 8,
            GridHeight = 8
        };
        _motionDetector = new MotionDetectionBlock(_motionSettings);
        _motionDetector.OnMotionDetected += OnMotionDetected;

        // Video tee: preview + encoder
        _videoTee = new TeeBlock(2, MediaBlockPadMediaType.Video);

        // Video renderer (preview)
        _videoRenderer = new VideoRendererBlock(_pipeline, VideoView1);

        // H264 encoder for the recording branch
        _h264Encoder = new H264EncoderBlock();

        // Pre-event recording block
        var preEventSettings = new PreEventRecordingSettings
        {
            PreEventDuration = TimeSpan.FromSeconds(10),
            PostEventDuration = TimeSpan.FromSeconds(5)
        };
        _preEventBlock = new PreEventRecordingBlock(preEventSettings, "mp4mux");
        _preEventBlock.AudioEnabled = audioEnabled;

        // Subscribe to recording events
        _preEventBlock.OnRecordingStarted += (s, args) =>
            Log($"Recording started: {args.Filename}");
        _preEventBlock.OnRecordingStopped += (s, args) =>
            Log($"Recording stopped: {args.Filename}");
        _preEventBlock.OnStateChanged += (s, args) =>
            Log($"State changed: {args.State}");

        // Connect video: source -> motion detector -> tee -> [renderer, encoder -> preEvent]
        _pipeline.Connect(_videoSource, _motionDetector);
        _pipeline.Connect(_motionDetector, _videoTee);
        _pipeline.Connect(_videoTee, _videoRenderer);
        _pipeline.Connect(_videoTee, _h264Encoder);
        _pipeline.Connect(_h264Encoder.Output, _preEventBlock.VideoInput);

        // Connect audio: source -> tee -> [renderer, encoder -> preEvent]
        if (audioEnabled)
        {
            var audioDevice = (await DeviceEnumerator.Shared.AudioSourcesAsync()).FirstOrDefault();
            if (audioDevice != null)
            {
                _audioSource = new SystemAudioSourceBlock(audioDevice.CreateSourceSettings(null));
                _audioTee = new TeeBlock(2, MediaBlockPadMediaType.Audio);
                _audioRenderer = new AudioRendererBlock();
                _aacEncoder = new AACEncoderBlock();

                _pipeline.Connect(_audioSource, _audioTee);
                _pipeline.Connect(_audioTee, _audioRenderer);
                _pipeline.Connect(_audioTee, _aacEncoder);
                _pipeline.Connect(_aacEncoder.Output, _preEventBlock.AudioInput);
            }
        }

        // Start pipeline — buffering begins immediately
        await _pipeline.StartAsync();

        // Start status timer to display buffer stats
        _statusTimer = new System.Timers.Timer(500);
        _statusTimer.Elapsed += (s, args) => UpdateStatus();
        _statusTimer.Start();

        Log("Pipeline started. Buffering...");
    }

    // Motion detection handler: auto-trigger recording on motion
    private void OnMotionDetected(object sender, MotionDetectionEventArgs e)
    {
        if (_preEventBlock == null) return;

        bool isMotion = e.Level >= _motionSettings.MotionThreshold;
        if (!isMotion) return;

        var state = _preEventBlock.State;
        if (state == PreEventRecordingState.Buffering)
        {
            var filename = Path.Combine(_outputFolder,
                $"motion_{DateTime.Now:yyyyMMdd_HHmmss}.mp4");
            _preEventBlock.TriggerRecording(filename);
            Log($"Motion triggered recording: {filename}");
        }
        else if (state == PreEventRecordingState.Recording ||
                 state == PreEventRecordingState.PostEventRecording)
        {
            // Motion still active — extend the recording
            _preEventBlock.ExtendRecording();
        }
    }

    // Manual trigger button
    private void BtTrigger_Click(object sender, RoutedEventArgs e)
    {
        if (_preEventBlock == null) return;

        var filename = Path.Combine(_outputFolder,
            $"event_{DateTime.Now:yyyyMMdd_HHmmss}.mp4");
        _preEventBlock.TriggerRecording(filename);
        Log($"Trigger recording: {filename}");
    }

    // Manual stop recording button
    private void BtStopRec_Click(object sender, RoutedEventArgs e)
    {
        _preEventBlock?.StopRecording();
        Log("Recording stopped manually.");
    }

    // Extend recording button
    private void BtExtend_Click(object sender, RoutedEventArgs e)
    {
        _preEventBlock?.ExtendRecording();
        Log("Post-event timer extended.");
    }

    // Monitor buffer status periodically
    private void UpdateStatus()
    {
        if (_preEventBlock == null) return;

        var state = _preEventBlock.State;
        var totalBytes = _preEventBlock.BufferTotalBytes;
        var duration = _preEventBlock.BufferedDuration;

        Dispatcher.Invoke(() =>
        {
            lbState.Text = $"State: {state}";
            lbBufferStats.Text = $"Buffer: {totalBytes / 1024.0:F1} KB, {duration.TotalSeconds:F1}s";
        });
    }

    // Stop pipeline and clean up
    private async void BtStop_Click(object sender, RoutedEventArgs e)
    {
        _statusTimer?.Stop();
        _statusTimer?.Dispose();

        if (_pipeline != null)
        {
            await _pipeline.StopAsync();
            _pipeline.Dispose();
            _pipeline = null;
        }

        if (_motionDetector != null)
        {
            _motionDetector.OnMotionDetected -= OnMotionDetected;
            _motionDetector = null;
        }

        _preEventBlock = null;
        _videoSource = null;
        _audioSource = null;

        Log("Pipeline stopped.");
    }
}
```

## Explanation of the Code

1. **Video Source**: The `SystemVideoSourceBlock` captures video from a local camera device. For RTSP IP cameras, use `RTSPSourceBlock` with `RTSPSourceSettings.CreateAsync()` instead.
2. **Motion Detection**: The `MotionDetectionBlock` performs frame-differencing-based motion detection without requiring OpenCV. It fires `OnMotionDetected` events that the application uses to automatically trigger recordings.
3. **Video Tee**: The `TeeBlock` splits the video stream into two branches — one for live preview via `VideoRendererBlock`, and one for H.264 encoding and pre-event buffering.
4. **H264 Encoder**: The `H264EncoderBlock` encodes raw video frames for the pre-event block. The block automatically selects the best available encoder (hardware-accelerated if available).
5. **PreEventRecordingBlock**: The core component. It receives encoded video and audio, stores them in a ring buffer, and creates dynamic output files on trigger. The `"mp4mux"` parameter sets MP4 as the output format.
6. **Audio Path**: Audio follows a similar pattern — tee splits to renderer (playback) and AAC encoder, which feeds into the pre-event block.
7. **Event Handling**: Three events notify your application:

   - `OnRecordingStarted` — fired when buffer flush begins
   - `OnRecordingStopped` — fired when recording finishes
   - `OnStateChanged` — fired on every state transition
8. **Status Monitoring**: A timer periodically reads `BufferTotalBytes` and `BufferedDuration` to display buffer health in the UI.

### Using an RTSP source

When using an RTSP IP camera instead of a local camera, replace the source setup:

```
// Replace SystemVideoSourceBlock with RTSPSourceBlock
var rtspSettings = await RTSPSourceSettings.CreateAsync(
    new Uri("rtsp://192.168.1.21:554/Streaming/Channels/101"),
    login: "admin",
    password: "password",
    audioEnabled: true);

var rtspSource = new RTSPSourceBlock(rtspSettings);

// Set audioEnabled before _preEventBlock.AudioEnabled, so no audio branch waits on a stream that never comes.

// The audio branch takes the RTSP audio in place of the system audio device:

    _audioRenderer = new AudioRendererBlock();
    _aacEncoder = new AACEncoderBlock();

    _pipeline.Connect(rtspSource.AudioOutput, _audioTee.Input);
    _pipeline.Connect(_audioTee, _audioRenderer);
    _pipeline.Connect(_audioTee, _aacEncoder);
    _pipeline.Connect(_aacEncoder.Output, _preEventBlock.AudioInput);
}
```

## Key Considerations

- **Memory usage**: 30 seconds of buffered H.264 video at 4 Mbps plus AAC audio at 128 kbps uses approximately 15.5 MB of managed memory per camera. Scale accordingly when monitoring multiple cameras.
- **Keyframe alignment**: The actual pre-event duration in the output file may be slightly less than configured, as the buffer drains from its earliest keyframe. With a typical 2-second GOP, the actual pre-event footage starts within 2 seconds of the configured duration.
- **Re-trigger behavior**: Calling `TriggerRecording()` while already recording extends the current recording rather than creating a new file. Call `StopRecording()` first if you need a new file.
- **Container format**: Use MP4 for maximum compatibility. Use MPEG-TS for crash safety in unattended/headless deployments where power loss or crashes may occur.
- **Encoded input required**: The `PreEventRecordingBlock` expects encoded frames. When using sources that output raw video (like `SystemVideoSourceBlock`), add encoder blocks (H264, HEVC) between the source and the pre-event block.

## Best Practices

- Set `PreEventDuration` based on your application requirements — longer buffers use more memory but capture more context
- Use `MaxBufferBytes` as a safety net in multi-camera systems to prevent unbounded memory growth
- Subscribe to `OnRecordingStopped` to confirm recordings were finalized successfully
- Use MPEG-TS for surveillance applications running unattended
- Implement a file naming strategy that includes timestamps (e.g., `event_2024-01-15_14-30-00.mp4`) for easy organization
- Monitor `BufferTotalBytes` periodically to verify the buffer is being populated and evicted correctly

# Intel RealSense Depth Camera in C# .NET

[Media Blocks SDK .NET](https://www.visioforge.com/media-blocks-sdk-net)

This guide shows how to use an Intel RealSense depth camera (D400 series, such as the D435) from a C# application with the `RealSenseSourceBlock`: list the cameras and their modes, show color and depth side by side, read the distance at a pixel, and record the depth view to an MP4 file. The same pipeline code runs on Windows x64, Windows ARM64 and Linux x64.

A RealSense camera's color stream is ordinary UVC video, so any capture source can show it. The depth (16-bit distance per pixel) and infrared streams are not: Windows capture APIs mislabel or reject them. `RealSenseSourceBlock` opens the camera through librealsense instead and gives every stream its own output in a format the rest of the pipeline understands.

## What the Block Delivers

| Output | Format | Enabled by |
| --- | --- | --- |
| `ColorOutput` | RGB | `RealSenseSourceSettings.Color` |
| `DepthOutput` | RGB (colorized, default) or `GRAY16_LE` (raw) | `RealSenseSourceSettings.Depth`, `DepthMode` |
| `InfraredOutput` | `GRAY8` | `RealSenseSourceSettings.Infrared` |

The streams come from one librealsense pipeline, so their frames are synchronized. With `AlignDepthToColor` the depth image is mapped onto the color image: it gets the color size, and the same pixel shows the same point in both. `GetDistance(x, y)` returns the distance in meters at a pixel of the latest depth frame.

```
graph LR;
    RealSenseSourceBlock-- color -->VideoRendererBlock1;
    RealSenseSourceBlock-- depth -->TeeBlock;
    TeeBlock-->VideoRendererBlock2;
    TeeBlock-->H264EncoderBlock;
    H264EncoderBlock-->MP4SinkBlock;
```

## Prerequisites

## Step 1: List the Cameras and Their Modes

## Step 2: Show Color and Depth Side by Side

Call `await VisioForgeX.InitSDKAsync()` once before you build a pipeline, for example in the window's `Loaded` handler. This WPF window has two `VideoView` controls, `VideoViewColor` and `VideoViewDepth`. The depth is aligned to the color image and colorized, so it can go straight to a renderer. The window's code-behind needs the `using` directives from Step 1. `StartAsync` returns `false` when the camera lacks the mode (`FindProfile` returned `null`) or the pipeline does not start; why a pipeline did not start comes in `OnError`.

```
private MediaBlocksPipeline _pipeline;
private RealSenseSourceBlock _source;
private readonly System.Timers.Timer _distanceTimer = new System.Timers.Timer(500);

private async Task<bool> StartAsync(RealSenseDeviceInfo camera)
{
    var settings = new RealSenseSourceSettings(camera.SerialNumber)
    {
        Color = camera.FindProfile(RealSenseStreamType.Color, 640, 480, 30),
        Depth = camera.FindProfile(RealSenseStreamType.Depth, 640, 480, 30),
        AlignDepthToColor = true,
        DepthMode = RealSenseDepthMode.Colorized,
    };

    // FindProfile returns null for a mode the camera does not have: pick another one from camera.Profiles.
    if (settings.Color == null || settings.Depth == null)
    {
        return false;
    }

    _pipeline = new MediaBlocksPipeline();
    _pipeline.OnError += (s, e) => Debug.WriteLine(e.Message);

    _source = new RealSenseSourceBlock(settings);
    _pipeline.Connect(_source.ColorOutput, new VideoRendererBlock(_pipeline, VideoViewColor) { IsSync = false }.Input);
    _pipeline.Connect(_source.DepthOutput, new VideoRendererBlock(_pipeline, VideoViewDepth) { IsSync = false }.Input);

    if (await _pipeline.StartAsync())
    {
        return true;
    }

    // The start failed: dispose the pipeline so that it releases the camera.
    await StopAsync();
    return false;
}

private async Task StopAsync()
{
    _distanceTimer.Stop();
    var pipeline = _pipeline;
    _pipeline = null;
    _source = null;
    if (pipeline == null)
    {
        return;
    }

    try
    {
        await pipeline.StopAsync();
    }
    finally
    {
        await pipeline.DisposeAsync();
    }
}
```

`IsSync = false` shows each frame as soon as it arrives, which is what a live camera preview needs. Leave a stream's profile `null` to keep it off; an output that is enabled but not connected is discarded.

## Step 3: Measure the Distance at a Pixel

`GetDistance(x, y)` reads the latest depth frame. It returns meters, or 0 when the camera has no depth for that pixel (too close, too far, or a surface it cannot see) or before the first frame. With `AlignDepthToColor = true` the coordinates are color-image pixels, so one pixel position works for both images. A mouse position on a `VideoView` is not a frame pixel: the view scales the frame to fit, so convert the position to frame coordinates before you call `GetDistance`.

```
public MainWindow()
{
    InitializeComponent();
    _distanceTimer.Elapsed += (s, e) => UpdateDistance();
}

private void UpdateDistance()
{
    var source = _source;
    if (source == null)
    {
        return;
    }

    // With alignment the depth frame has the color size.
    var profile = source.Settings.AlignDepthToColor ? source.Settings.Color : source.Settings.Depth;
    float meters;
    try
    {
        meters = source.GetDistance(profile.Width / 2, profile.Height / 2);
    }
    catch (Exception ex)
    {
        // The timer would swallow it.
        Debug.WriteLine(ex);
        return;
    }

    Dispatcher.BeginInvoke((Action)(() => lbDistance.Text = $"Distance at center: {meters:F2} m"));
}
```

Start the timer when `StartAsync` returns `true`; `StopAsync` in Step 2 stops it, and the `Closing` handler in Step 4 disposes it. A pixel outside the depth frame throws `ArgumentOutOfRangeException`; the timer swallows exceptions thrown by its `Elapsed` handler, so catch and log them in `UpdateDistance`.

## Step 4: Record the Depth View to MP4

The colorized depth is a normal RGB video, so it can be encoded like any camera. Split it with a `TeeBlock`: one branch to the screen, one to an H.264 encoder and an MP4 file. In `StartAsync`, these lines replace the Step 2 line that connects `DepthOutput` to the renderer, before `await _pipeline.StartAsync()`; an output connects to one block only.

```
var tee = new TeeBlock(2, MediaBlockPadMediaType.Video);
_pipeline.Connect(_source.DepthOutput, tee.Input);
_pipeline.Connect(tee.Outputs[0], new VideoRendererBlock(_pipeline, VideoViewDepth) { IsSync = false }.Input);

var encoder = new H264EncoderBlock();
var mp4 = new MP4SinkBlock(new MP4SinkSettings(System.IO.Path.Combine(Environment.GetFolderPath(Environment.SpecialFolder.MyVideos, Environment.SpecialFolderOption.Create), "depth.mp4")));
_pipeline.Connect(tee.Outputs[1], encoder.Input);
_pipeline.Connect(encoder.Output, mp4.CreateNewInput(MediaBlockPadMediaType.Video));
```

`StopAsync` finishes the file, so await it before the window closes and before the application exits. With `Closing="Window_Closing"` on the window, cancel the first close, stop, then close again:

```
private async void Window_Closing(object sender, System.ComponentModel.CancelEventArgs e)
{
    // Stop the camera first, then close for real once this handler has returned.
    if (_pipeline != null)
    {
        e.Cancel = true;
        IsEnabled = false;
        try
        {
            await StopAsync();
        }
        catch (Exception ex)
        {
            Debug.WriteLine(ex);
        }

        Dispatcher.BeginInvoke(new Action(Close));
        return;
    }

    _distanceTimer.Dispose();

    // The application's last SDK window: shut the SDK down.
    VisioForgeX.DestroySDK();
}
```

A colorized image is for people to look at: the colors stand for distances, but the exact values are gone. To keep distances, either call `GetDistance` while you capture, or set `DepthMode = RealSenseDepthMode.Raw`. The depth output then carries the camera's 16-bit values (`GRAY16_LE`); multiply a value by `DepthScale` to get meters. `DepthScale` is known once the pipeline has started. Raw depth is for your own processing: the H.264 chain above reduces it to 8 bits, so do not record it that way.

# Show RTSP IP Cameras in a Web Browser with WHEP in C# / .NET

[Media Blocks SDK .NET](https://www.visioforge.com/media-blocks-sdk-net)

Demo Sample

The code in this guide comes from the RTSP WHEP Camera Grid Demo (WPF) in the [samples repository](https://github.com/visioforge/.Net-SDK-s-samples/tree/master/Media%20Blocks%20SDK/WPF/CSharp/RTSP%20WHEP%20Camera%20Grid%20Demo): it adds cameras by RTSP URL, serves a grid page with every camera, and forwards each camera's WHEP requests to its own server. Its console version, [RTSP WHEP Camera Grid (Console)](https://github.com/visioforge/.Net-SDK-s-samples/tree/master/Media%20Blocks%20SDK/Console/RTSP%20WHEP%20Camera%20Grid), does the same on Windows, macOS and Linux, with the camera URLs on the command line. Both demos need Media Blocks SDK .NET 2026.11.23 or later, the first release with WHEP audio.

The block reference is in [Sink blocks → WHEP server](../../Sinks/#whep-server).

## What You Will Build

A browser cannot open an RTSP URL. The usual ways to put an IP camera on a web page are to transcode it to HLS (several seconds of delay and a decoder plus an encoder per camera) or to run a separate media server next to your application. This guide takes a third route: your .NET application itself becomes a WebRTC server, the camera's H.264 goes to the browser exactly as the camera sent it, and the camera's audio goes with it as Opus.

The pipeline for one camera is two blocks for the video, and a decoder for the audio:

```
graph LR;
    cam["IP camera"] -- "RTSP, H.264 + AAC" --> RTSPRAWSourceBlock;
    subgraph app ["Your .NET application"]
        RTSPRAWSourceBlock -- "H.264, not decoded" --> WHEPServerSinkBlock;
        RTSPRAWSourceBlock -- "AAC / G.711" --> DecodeBinBlock;
        DecodeBinBlock -- "PCM" --> WHEPServerSinkBlock;
    end
    WHEPServerSinkBlock -- WebRTC --> b1["Browser"];
    WHEPServerSinkBlock -- WebRTC --> b2["Browser"];
```

- `RTSPRAWSourceBlock` connects to the camera and outputs its encoded H.264 without decoding it, and its encoded audio.
- `DecodeBinBlock` decodes the camera's AAC or G.711. Browsers take Opus over WebRTC, so the audio cannot be passed through as the video is.
- `WHEPServerSinkBlock` runs a WHEP (WebRTC-HTTP Egress Protocol) server. A browser posts a WebRTC offer to it over HTTP, gets an answer, and receives the video and the audio over its own WebRTC session. The block encodes the audio to Opus for each viewer.

What this buys you:

- **Sub-second latency.** The browser plays the stream over WebRTC, not through a segment-based protocol.
- **Almost no CPU for the video, for any number of viewers.** The video is never decoded or encoded: the block sends the camera's stream to every viewer as it arrives. The audio is decoded once per camera and encoded to Opus for each viewer. Each viewer still costs network bandwidth equal to the camera's bitrate.
- **No media server.** The WHEP server runs inside your process; the browser side is about 20 lines of JavaScript with no player library.

WHEP is a small HTTP protocol on top of WebRTC: one `POST` with the SDP offer, a `201 Created` with the SDP answer and a `Location` header for the session, and a `DELETE` on that `Location` when the viewer leaves. Any WHEP player can use the endpoint, not only the page in this guide.

## The One Thing to Know First: Same Origin

The WHEP server sends no CORS headers. A browser therefore accepts its answers only on a page served from the same address and port as the endpoint. Opening `index.html` from disk, or serving it from another port, fails at the `fetch` of the offer.

The demo solves it the simple way: the application runs a small HTTP server for the page and forwards every request under `/whep/` to the WHEP server, which itself listens on loopback only. The browser talks to one origin; the WHEP server is never exposed directly.

```
sequenceDiagram
    participant Browser
    participant Page as Page server (your app)
    participant WHEPServerSinkBlock
    Browser->>Page: GET /
    Page-->>Browser: index.html
    Browser->>Page: POST /whep/endpoint (SDP offer)
    Page->>WHEPServerSinkBlock: POST /whep/endpoint
    WHEPServerSinkBlock-->>Page: 201 Created, SDP answer, Location
    Page-->>Browser: 201 Created, SDP answer, Location
    WHEPServerSinkBlock-)Browser: camera H.264 and Opus audio over WebRTC
    Browser->>Page: DELETE Location (page closed)
    Page->>WHEPServerSinkBlock: DELETE Location
```

Only the HTTP exchange goes through the page server. The video and the audio travel over the WebRTC connection that the offer and answer set up.

## One Camera: the Complete Server

The console program below is a single-camera version of the console demo. It builds the pipeline, serves the embedded `index.html` on `http://localhost:8080/` and forwards `/whep/...` to the WHEP server on `127.0.0.1:9100`.

```
using System;
using System.IO;
using System.Net;
using System.Net.Http;
using System.Threading.Tasks;

using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.Special;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.Sources;

const string PageUrl = "http://localhost:8080/";
const string WhepServer = "http://127.0.0.1:9100";

await VisioForgeX.InitSDKAsync();

using var http = new HttpClient();
MediaBlocksPipeline? pipeline = null;
HttpListener? pageServer = null;

try
{
    if (!WHEPServerSinkBlock.IsAvailable())
    {
        Console.WriteLine("WHEPServerSinkBlock is not available: add the VisioForge.CrossPlatform.Core.*.Adds package for this platform.");
        return;
    }

    pipeline = new MediaBlocksPipeline();
    pipeline.OnError += (s, e) => Console.WriteLine(e.Message);

    // Encoded H.264 straight from the camera, and its audio if it has any (CreateAsync turns audio off otherwise).
    var rtspSettings = await RTSPRAWSourceSettings.CreateAsync(new Uri("rtsp://192.168.1.64:554/stream1"), "admin", "password", audioEnabled: true);
    var rtsp = new RTSPRAWSourceBlock(rtspSettings);

    // The WHEP server listens on loopback only; browsers reach it through the page server below.
    var whep = new WHEPServerSinkBlock(new WHEPServerSinkSettings { ServerAddress = WhepServer });
    whep.ConsumerAdded += (s, e) => Console.WriteLine($"Viewer connected: {e.PeerId}");
    whep.ConsumerRemoved += (s, e) => Console.WriteLine($"Viewer left: {e.PeerId}");

    pipeline.Connect(rtsp.VideoOutput, whep.VideoInput);

    // Browsers take Opus, not the camera's AAC or G.711: decode it here, the WHEP server encodes it to Opus.
    if (rtspSettings.AudioEnabled)
    {
        var audioDecoder = new DecodeBinBlock(renderVideo: false, renderAudio: true, renderSubtitle: false);
        pipeline.Connect(rtsp.AudioOutput, audioDecoder.Input);
        pipeline.Connect(audioDecoder.AudioOutput, whep.AudioInput);
    }

    // The page and the WHEP requests share one origin: whepserversink sends no CORS headers.
    pageServer = new HttpListener();
    pageServer.Prefixes.Add(PageUrl);
    pageServer.Start();
    _ = ServePageAsync(pageServer);

    if (await pipeline.StartAsync())
    {
        Console.WriteLine($"Open {PageUrl} in a browser. Press Enter to stop.");
        Console.ReadLine();
    }
}
catch (Exception ex)
{
    // CreateAsync throws when the camera cannot be read; HttpListener.Start when the page port is taken.
    Console.WriteLine(ex.Message);
}
finally
{
    pageServer?.Close();

    if (pipeline != null)
    {
        await pipeline.StopAsync();
        await pipeline.DisposeAsync();
    }

    VisioForgeX.DestroySDK();
}

async Task ServePageAsync(HttpListener server)
{
    while (server.IsListening)
    {
        HttpListenerContext context;
        try
        {
            context = await server.GetContextAsync();
        }
        catch (Exception ex) when (ex is HttpListenerException || ex is ObjectDisposedException)
        {
            return;
        }

        _ = HandleRequestAsync(context);
    }
}

async Task HandleRequestAsync(HttpListenerContext context)
{
    var request = context.Request;
    var response = context.Response;

    try
    {
        var path = request.Url?.AbsolutePath ?? string.Empty;

        if (path == "/")
        {
            // The page embedded by the .csproj above.
            using var page = System.Reflection.Assembly.GetEntryAssembly()!.GetManifestResourceStream("index.html")!;
            using var html = new MemoryStream();
            await page.CopyToAsync(html);
            await WriteAsync(response, "text/html", html.ToArray());
        }
        else if (path.StartsWith("/whep/", StringComparison.Ordinal))
        {
            // The offer and the session's DELETE go to the WHEP server unchanged.
            using var forward = new HttpRequestMessage(new HttpMethod(request.HttpMethod), WhepServer + path);
            if (request.HasEntityBody)
            {
                using var body = new MemoryStream();
                await request.InputStream.CopyToAsync(body);
                forward.Content = new ByteArrayContent(body.ToArray());
                forward.Content.Headers.TryAddWithoutValidation("Content-Type", request.ContentType);
            }

            using var reply = await http.SendAsync(forward);
            if (reply.Headers.Location != null)
            {
                // The session URL the player deletes when it leaves.
                response.Headers["Location"] = reply.Headers.Location.OriginalString;
            }

            response.StatusCode = (int)reply.StatusCode;
            await WriteAsync(response, reply.Content.Headers.ContentType?.ToString(), await reply.Content.ReadAsByteArrayAsync());
        }
        else
        {
            response.StatusCode = 404;
        }
    }
    catch (Exception ex)
    {
        Console.WriteLine(ex.Message);
        response.StatusCode = 502;
    }
    finally
    {
        response.Close();
    }
}

static async Task WriteAsync(HttpListenerResponse response, string? contentType, byte[] body)
{
    if (contentType != null)
    {
        response.ContentType = contentType;
    }

    response.ContentLength64 = body.Length;
    await response.OutputStream.WriteAsync(body);
}
```

What each part does:

- **`RTSPRAWSourceSettings.CreateAsync`** connects to the camera and reads its stream description before the pipeline is built. With `audioEnabled: true` it keeps the camera's audio, and turns `AudioEnabled` off when the camera sends none — the code connects the audio only then. `CreateAsync` throws `InvalidOperationException` when it cannot read the stream — the camera is offline, the URL is wrong, or the credentials are refused.
- **`RTSPRAWSourceBlock.VideoOutput`** carries the camera's encoded H.264. Connecting it straight to **`WHEPServerSinkBlock.VideoInput`** (the same pad as `Input`) is the whole video path: no decoder, no encoder.
- **`RTSPRAWSourceBlock.AudioOutput`** carries the camera's encoded audio. **`DecodeBinBlock`** with only `renderAudio` decodes it, and **`WHEPServerSinkBlock.AudioInput`** takes the raw audio and encodes it to Opus for each viewer. A mono camera reaches the browser as two identical channels.
- **`WHEPServerSinkSettings.ServerAddress`** is the address the WHEP server listens on. `127.0.0.1` keeps it reachable from this machine only, which is what you want when the page server forwards to it. The block's `EndpointUrl` property returns the URL players post to — here `http://127.0.0.1:9100/whep/endpoint`.
- **`ConsumerAdded` / `ConsumerRemoved`** report each viewer that connects and leaves, with its session ID in `PeerId`. They are raised on a GStreamer thread: in a UI application marshal to the UI thread without blocking it — the demo uses `Dispatcher.BeginInvoke`. `ConsumerRemoved` is not raised for viewers still connected when the pipeline stops; their sessions end with it.
- **`try` / `finally`** reports what went wrong — `CreateAsync` failing on the camera, `HttpListener.Start` on a taken port — and the `finally` closes the page server, stops and disposes the pipeline and calls `VisioForgeX.DestroySDK()` whether start-up succeeded or failed.
- **The page server** uses `HttpListener`, which serves `http://localhost:<port>/` without administrator rights. It answers `/` with the page, forwards `/whep/...` with the same method, body and `Content-Type`, and copies the status code, the answer body and the `Location` header back to the browser.

The page server is started before the pipeline, so the page is reachable as soon as the stream is.

## The Browser Side: a Minimal WHEP Player

Put this file in `wwwroot/index.html`. The `play` function is the demo's player with one addition, the `iceServers` list passed to `RTCPeerConnection` (see [NAT, STUN and TURN](#nat-stun-and-turn)):

```
<!doctype html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <title>Camera</title>
    <style>
        body { margin: 0; background: #111; color: #ddd; font-family: sans-serif; }
        figure { margin: 0; position: relative; background: #000; }
        video { width: 100%; aspect-ratio: 16 / 9; display: block; }
        figcaption { position: absolute; left: 8px; top: 6px; font-size: 13px; text-shadow: 0 0 3px #000; }
    </style>
</head>
<body>
<figure>
    <video id="video" autoplay muted playsinline controls></video>
    <figcaption id="caption" data-name="Camera">Camera</figcaption>
</figure>
<script>
    // STUN/TURN servers for the viewer's side of the connection; empty is enough on a local network.
    const iceServers = [];

    // A minimal WHEP player: offer, POST it to the endpoint, apply the answer.
    async function play(endpoint, video, caption) {
        const pc = new RTCPeerConnection({ iceServers });
        pc.addTransceiver('video', { direction: 'recvonly' });
        pc.addTransceiver('audio', { direction: 'recvonly' });
        // Video and audio arrive as two tracks; both go into the one stream the video element plays.
        video.srcObject = new MediaStream();
        pc.ontrack = e => video.srcObject.addTrack(e.track);

        await pc.setLocalDescription(await pc.createOffer());
        // Send the offer with all ICE candidates in it.
        await new Promise(resolve => {
            if (pc.iceGatheringState === 'complete') resolve();
            else pc.onicegatheringstatechange = () => pc.iceGatheringState === 'complete' && resolve();
        });

        const response = await fetch(endpoint, { method: 'POST', headers: { 'Content-Type': 'application/sdp' }, body: pc.localDescription.sdp });
        if (response.status !== 201) throw new Error(`${endpoint}: HTTP ${response.status}`);
        await pc.setRemoteDescription({ type: 'answer', sdp: await response.text() });

        // End the session on the server when the page closes.
        const session = response.headers.get('Location');
        addEventListener('pagehide', () => fetch(session, { method: 'DELETE', keepalive: true }));
        pc.onconnectionstatechange = () => caption.textContent = `${caption.dataset.name} - ${pc.connectionState}`;
    }

    const caption = document.getElementById('caption');
    play('/whep/endpoint', document.getElementById('video'), caption).catch(e => caption.textContent = e.message);
</script>
</body>
</html>
```

Step by step:

1. **Receive-only video and audio transceivers.** The page only watches and listens, so it offers to receive one video and one audio track and sends nothing. A camera without audio leaves the audio part of the answer inactive and the video plays alone.
2. **Wait for ICE gathering to complete** before sending the offer. All network candidates then travel inside the single `POST`, so the player never needs WHEP's `PATCH` requests for trickle ICE.
3. **`POST` the SDP offer** with `Content-Type: application/sdp`. The server answers `201 Created` with the SDP answer in the body.
4. **Apply the answer.** WebRTC connects and `ontrack` adds each track, video and audio, to the stream the `<video>` element plays.
5. **Delete the session on `pagehide`.** The `Location` header names the session; `keepalive: true` lets the `DELETE` go out while the page unloads. The server then raises `ConsumerRemoved`.

The `<video>` element is `muted`, which lets the browser start playback without a click, `controls` lets the viewer unmute it, and `playsinline` is for mobile browsers. Browsers do not autoplay sound before the viewer interacts with the page, so a page that should play the sound at once unmutes from a click handler. The caption shows the connection state (`connecting`, `connected`, `failed`), which is the first thing to look at when a tile stays black.

## Scaling to Several Cameras

A `WHEPServerSinkBlock` serves one camera. For several cameras the demo runs one block per camera, each on its own port, and gives each camera its own path on the page server.

The pipeline part, from the demo's start handler — one `RTSPRAWSourceBlock` → `WHEPServerSinkBlock` pair per camera, with a `DecodeBinBlock` for each camera that has audio, WHEP ports counted up from 9100:

```
for (var i = 0; i < _cameras.Count; i++)
{
    var camera = _cameras[i];

    // Encoded H.264 straight from the camera, and its audio if it has any (CreateAsync turns audio off otherwise).
    var rtspSettings = await RTSPRAWSourceSettings.CreateAsync(camera.Url, camera.Login, camera.Password, audioEnabled: true);
    var rtsp = new RTSPRAWSourceBlock(rtspSettings);

    // One WHEP server per camera; only this app talks to it, the browsers go through the page server below.
    var whep = new WHEPServerSinkBlock(new WHEPServerSinkSettings { ServerAddress = $"http://127.0.0.1:{FirstWhepPort + i}" });
    whep.ConsumerAdded += (s, args) => UpdateViewers(+1);
    whep.ConsumerRemoved += (s, args) => UpdateViewers(-1);

    _pipeline.Connect(rtsp.VideoOutput, whep.VideoInput);

    // Browsers take Opus, not the camera's AAC or G.711: decode it here, the WHEP server encodes it to Opus.
    if (rtspSettings.AudioEnabled)
    {
        var audioDecoder = new DecodeBinBlock(renderVideo: false, renderAudio: true, renderSubtitle: false);
        _pipeline.Connect(rtsp.AudioOutput, audioDecoder.Input);
        _pipeline.Connect(audioDecoder.AudioOutput, whep.AudioInput);
    }
}
```

The routing part: the page server forwards `/cam/N/whep/...` to camera N's server and puts the same `/cam/N` prefix in front of the `Location` it returns, so that the browser's `DELETE` reaches the right camera too:

```
var path = request.Url?.AbsolutePath ?? string.Empty;
var parts = path.Split('/', 4, StringSplitOptions.RemoveEmptyEntries);

if (parts.Length == 4 && parts[0] == "cam" && int.TryParse(parts[1], out var camera) && camera >= 0 && camera < _cameras.Count)
{
    // /cam/N/whep/... is forwarded to camera N's WHEP server.
    using var forward = new HttpRequestMessage(new HttpMethod(request.HttpMethod), $"http://127.0.0.1:{FirstWhepPort + camera}/{parts[2]}/{parts[3]}");
    if (request.HasEntityBody)
    {
        using var body = new MemoryStream();
        await request.InputStream.CopyToAsync(body);
        forward.Content = new ByteArrayContent(body.ToArray());
        forward.Content.Headers.TryAddWithoutValidation("Content-Type", request.ContentType);
    }

    using var reply = await _http.SendAsync(forward);
    if (reply.Headers.Location != null)
    {
        // The session URL the player deletes when it leaves, under the same /cam/N prefix.
        response.Headers["Location"] = $"/cam/{camera}{reply.Headers.Location.OriginalString}";
    }

    response.StatusCode = (int)reply.StatusCode;
    await WriteAsync(response, reply.Content.Headers.ContentType?.ToString(), await reply.Content.ReadAsByteArrayAsync());
}
```

The demo's page server also answers `/cameras` with the number of cameras, and the grid page builds one tile per camera with its `play` function — the one above, without the `iceServers` addition:

```
(async () => {
    const count = await (await fetch('/cameras')).json();
    for (let i = 0; i < count; i++) {
        const figure = document.createElement('figure');
        const video = Object.assign(document.createElement('video'), { autoplay: true, muted: true, playsInline: true, controls: true });
        const caption = document.createElement('figcaption');
        caption.dataset.name = caption.textContent = `Camera ${i}`;
        figure.append(video, caption);
        document.getElementById('grid').append(figure);

    }

```

With the CSS rule `#grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(420px, 1fr)); }` the tiles wrap to the window width.

Two design notes for a real NVR:

- **One pipeline or one per camera.** The demo puts every camera pair in one `MediaBlocksPipeline`, so they start and stop together, and a camera that cannot be read makes `CreateAsync` throw before the start. To restart one camera without touching the others, give each pair its own pipeline — the same pattern the [Multi-Camera RTSP Grid](../multi-camera-rtsp-grid/) guide uses for local rendering.
- **Bandwidth, not CPU, is the budget.** Every viewer of every tile receives the camera's full bitrate. For a grid, point the source at the camera's H.264 sub-stream and keep the main stream for single-camera views and for [recording without re-encoding](../rtsp-save-original-stream/).

## Limits to Know Before Shipping

### Codec: H.264 only

The block's input accepts encoded H.264 only. Raw video, or any other codec, fails to connect and the pipeline does not start: the block never encodes for viewers. An H.265 camera stream is refused for the same reason — most browsers cannot play H.265 over WebRTC anyway. Switch the camera, or its sub-stream, to H.264.

### H.264 profiles and browsers

The camera's stream reaches the browser untouched, so the browser's WebRTC decoder must take the camera's profile. Chromium-based browsers (Chrome, Edge) played a camera's 1080p Main profile H.264 in our tests. A browser whose WebRTC decoder takes only constrained baseline shows no picture for a Main or High profile camera. When one viewer sees an empty tile and another does not, open the page in Chrome or Edge, or switch the camera's stream to the Baseline profile if the camera offers one.

The SDK's own `WHEPSourceBlock` offers H.264 only as constrained baseline with the exact `profile-level-id` `42e016`, which camera streams do not match, so it gets no picture from this block. Use a browser, or a player that sends `level-asymmetry-allowed=1` as browsers do.

### Audio

`AudioInput` takes raw audio and the block encodes it to Opus for each viewer, the one audio codec every browser takes over WebRTC; already-encoded audio (the camera's AAC) fails to connect, so decode it first with `DecodeBinBlock`. A mono camera is sent as two identical channels. Connect the audio only when the camera has it: the WHEP server starts listening only once every connected input has delivered its format, so an audio input that receives nothing keeps it closed. `CreateAsync` turns `AudioEnabled` off for a camera without audio, which is the check the code above makes. Two cameras need `audioEnabled: false` instead: one that lists audio in its stream description but sends none, which keeps the server closed in the same way, and one whose audio codec has no decoder, which fails the pipeline — and in the camera grid above one pipeline carries every camera.

Opus is encoded for each viewer, so every viewer adds an audio encoder; the video, passed through, adds none.

### Listening address

`ServerAddress` takes `http://` addresses only and defaults to `http://127.0.0.1:9090`, which accepts players on this machine only; `http://0.0.0.0:<port>` accepts players from other machines. For a server listening on `0.0.0.0`, `EndpointUrl` names the loopback address — players on other machines use this machine's network address instead.

With the page-server pattern of this guide, keep the WHEP server on `127.0.0.1` and expose only the page server. The demo's page server listens on `localhost`; to show the cameras on other computers, put a reverse proxy (nginx, IIS, Caddy) in front of it, forward the same paths and set the `Host` header to `localhost:<port>`, because the page server answers no other host name.

### HTTPS

Receiving WebRTC needs no HTTPS, so plain `http://` works for viewers on the local network. The WHEP server itself speaks `http://` only; if your deployment needs HTTPS, terminate it in the server or reverse proxy that serves the page.

### NAT, STUN and TURN

Each side of a WebRTC connection gathers its own network candidates, so STUN and TURN are set on each side separately:

- **The server's side:** `StunServer` (`stun://hostname:port`) and `TurnServer` (`turn(s)://username:password@host:port`) in `WHEPServerSinkSettings`. Both are unset by default, which means no STUN server — enough on a local network.
- **The viewer's side:** the `iceServers` list the page passes to `RTCPeerConnection`. It is empty in the page above.

The signaller also announces the server's STUN server in a `Link` header of its answer, but the page server in this guide does not forward that header and the player does not read it, so the page sets its own `iceServers`.

```
var whep = new WHEPServerSinkBlock(new WHEPServerSinkSettings
{
    ServerAddress = "http://127.0.0.1:9100",
    StunServer = "stun://stun.l.google.com:19302",
    TurnServer = "turn://user:password@turn.example.com:3478"
});
```

```
const iceServers = [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'password' }
];
```

### Authentication

`WHEPServerSinkSettings` has no authentication setting: anyone who can reach the WHEP server's address can watch. Keep it on `127.0.0.1` and put your access control — login, session cookie, token check — in the page server that forwards the requests, before the forward.

### Errors the block reports

The block's build fails, with a message through the pipeline's `OnError` event, when `ServerAddress` is not an `http://` address with a port in 1–65535 or when its port is already in use. Give every camera its own free port.

### Platforms

Windows x64 with `VisioForge.CrossPlatform.Core.Windows.Adds.x64`, macOS with `VisioForge.CrossPlatform.Core.macOS.Adds`, Linux x64/arm64 with `VisioForge.CrossPlatform.Core.Linux.Adds.x64`/`.arm64` and the distribution's `gstreamer1.0-plugins-bad` and `gstreamer1.0-nice`, iOS with `VisioForge.CrossPlatform.Core.iOS` 2026.11.23 or later. Not on Android: the Android runtime, `VisioForge.CrossPlatform.Core.Android`, does not include the `rswebrtc` plugin, so `IsAvailable()` returns `false` there. Check `WHEPServerSinkBlock.IsAvailable()` at startup, as the demo does.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `WHEPServerSinkBlock.IsAvailable()` returns `false` | The platform's `Adds` package is not referenced (on iOS, `VisioForge.CrossPlatform.Core.iOS` is missing or the SDK is older than 2026.11.23), or on Linux the distribution packages listed in [Prerequisites](#prerequisites) are missing. |
| `CreateAsync` throws `InvalidOperationException` ("Unable to read RTSP stream info") | The camera is unreachable, or the URL or credentials are wrong. Open the same URL in another RTSP client to check it. |
| `StartAsync` returns `false` | Read the `OnError` messages: a port already in use, an invalid `ServerAddress`, or a camera stream that is not H.264 (H.265, MJPEG). |
| The video plays, no sound | The `<video>` element starts muted: unmute it with its controls. If the camera sends no audio, `CreateAsync` turned `AudioEnabled` off and no audio was connected; check the camera's audio setting. |
| The page shows `HTTP 502` with the audio connected | The audio input received nothing, so the WHEP server never started listening. Connect `AudioInput` only for a camera that sends audio; for a camera that lists audio but sends none, create the source with `audioEnabled: false`. |
| The page shows a `fetch` error such as `Failed to fetch` | The page and the endpoint are on different origins. Serve the page from the server that forwards `/whep/`, never from disk or from another port. |
| The page shows `HTTP 404` or `HTTP 502` | The page server did not forward the path, or the WHEP server is not running on the forwarded port. |
| The caption stays at `connecting`, then `failed` | The browser cannot reach the application machine over WebRTC. Check the firewall on that machine; for viewers outside the local network set STUN/TURN on both sides — `StunServer` and `TurnServer` for the server, `iceServers` in the page. |
| The caption says `connected`, the tile stays black | The browser's decoder does not take the camera's H.264 profile. Try Chrome or Edge, or the camera's Baseline profile. |
| No `ConsumerRemoved` for a viewer that is gone | The page sends its `DELETE` on `pagehide`; a browser that crashes or loses the network does not send it. Viewers still connected when the pipeline stops raise no event. |
| `HttpListener.Start` throws `HttpListenerException` | The page port is taken, or the prefix is not `localhost` and needs administrator rights. Choose another port or keep `localhost`. |

## WHEP Server, WebRTC, WHIP or HLS?

- **`WHEPServerSinkBlock`** (this guide) — the source is already H.264 (an IP camera) and the viewers are browsers on your network. Video passthrough with no encoder, audio encoded to Opus, no media server.
- **[`WebRTCSinkBlock`](../../Sinks/#webrtc)** — the video is raw or processed in the pipeline (a webcam, the screen, overlays, analytics). It encodes for each viewer (VP8 video, Opus audio) with per-viewer congestion control, at the cost of an encoder per viewer, and uses the `webrtcsink` WebSocket signalling protocol instead of WHEP.
- **[`WHIPSinkBlock`](../../Sinks/#whip)** — you already run a WebRTC media server (MediaMTX, Janus, Cloudflare Stream) and want the application to push one stream to it; the server then handles the viewers. Requires H.264 video and Opus audio; runs on Windows, macOS, Linux and iOS.
- **[HLS](../../Sinks/#hls)** — viewers on the open internet through a CDN or a plain `<video>` player, when a delay of several seconds is acceptable. See also [HLS streaming](../../../general/network-streaming/hls-streaming/) and the [ASP.NET Web Forms HLS player](../aspnet-webforms-hls-player/) guide.

## Frequently Asked Questions

### Can a browser play an RTSP stream directly?

No. Browsers do not implement RTSP. The stream has to reach the page over a protocol the browser supports — WebRTC, as in this guide, or HLS. With `WHEPServerSinkBlock` the camera's H.264 is carried over WebRTC without being converted.

### Does the application re-encode the video?

No. `RTSPRAWSourceBlock` outputs the camera's encoded H.264 and `WHEPServerSinkBlock` sends it to every viewer as it arrives. That is why the video costs almost no CPU however many viewers watch it, and also why the camera must send H.264 in a profile the browser can decode. Only the audio is re-encoded, to Opus.

### Do I need a media server such as MediaMTX or Janus?

No. The WHEP server runs inside your .NET process. You need a media server only if you want one to handle the viewers, for example on the internet — then push the stream to it with `WHIPSinkBlock`.

### How does the camera's audio reach the browser?

Browsers receive Opus over WebRTC, and IP cameras send AAC or G.711, so the audio cannot be passed through as the video is. Create the source with `audioEnabled: true`, decode `RTSPRAWSourceBlock.AudioOutput` with `DecodeBinBlock` and connect the decoder to `WHEPServerSinkBlock.AudioInput`: the block encodes it to Opus for each viewer. The page offers an audio transceiver and plays both tracks in one `<video>` element, which starts muted until the viewer unmutes it.

### Can I play the stream with something other than a browser?

Yes, any WHEP player can post an offer to the endpoint. The exception is the SDK's own `WHEPSourceBlock`, which offers only constrained baseline `42e016` and gets no picture from a camera stream.

### How many cameras and viewers can one application serve?

There is no per-viewer video encoding — only an Opus encoder per viewer for the audio — so the limit is network bandwidth: each viewer of each camera receives that camera's full bitrate. Use the cameras' sub-streams for grid views.

## Live RTSP Preview

The core pattern connects an RTSP source to video and audio renderers through a `MediaBlocksPipeline`. Initialize the SDK once at application startup, then create pipelines as needed.

```
using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.VideoRendering;
using VisioForge.Core.MediaBlocks.AudioRendering;
using VisioForge.Core.Types.X.Sources;

// Initialize SDK once at startup
await VisioForgeX.InitSDKAsync();

// Create the pipeline
var pipeline = new MediaBlocksPipeline();

// Connect to the RTSP camera
var rtspSettings = await RTSPSourceSettings.CreateAsync(
    new Uri("rtsp://192.168.1.21:554/Streaming/Channels/101"),
    "admin",          // login
    "password",       // password
    true);            // audio enabled

var rtspSource = new RTSPSourceBlock(rtspSettings);

// Create video renderer (VideoView1 is an IVideoView control on your form)
var videoRenderer = new VideoRendererBlock(pipeline, VideoView1);
pipeline.Connect(rtspSource.VideoOutput, videoRenderer.Input);

// Create audio renderer (optional)
var audioRenderer = new AudioRendererBlock();
// AudioOutput is null when the source was created with audioEnabled: false or the camera info shows no audio; in compatibility mode with audio on it exists even for a camera without audio.
if (rtspSource.AudioOutput != null)
{
    pipeline.Connect(rtspSource.AudioOutput, audioRenderer.Input);
}

// Start playback
await pipeline.StartAsync();
```

To stop playback and release resources:

```
await pipeline.StopAsync();
await pipeline.DisposeAsync();
```

## RTSP Authentication

Most IP cameras require credentials to access the video stream. You can provide authentication in two ways.

**Credentials as parameters** — pass username and password to `RTSPSourceSettings.CreateAsync()`:

```
var settings = await RTSPSourceSettings.CreateAsync(
    new Uri("rtsp://192.168.1.21:554/stream"),
    "admin",      // username
    "mypassword", // password
    true);        // audio enabled
```

**Credentials in the URL** — embed them directly in the RTSP URI:

```
var settings = await RTSPSourceSettings.CreateAsync(
    new Uri("rtsp://admin:mypassword@192.168.1.21:554/stream"),
    null, null, true);
```

For ONVIF cameras, authenticate through `ONVIFClientX` to retrieve the stream URI automatically — see the [ONVIF Camera Discovery](#onvif-camera-discovery) section below. Most cameras use digest authentication by default. If you encounter connection failures, verify that your camera's authentication mode matches (digest vs basic) and that the RTSP port (typically 554) is accessible.

## Low-Latency Mode

For real-time monitoring or PTZ control, enable low-latency mode to cut the jitter buffer from the default 500ms to 150ms. Set `Latency` to 150ms or less to go lower:

```
var rtspSettings = await RTSPSourceSettings.CreateAsync(
    new Uri("rtsp://192.168.1.21:554/stream"),
    "admin", "password", true);

rtspSettings.LowLatencyMode = true;

var rtspSource = new RTSPSourceBlock(rtspSettings);
var videoRenderer = new VideoRendererBlock(pipeline, VideoView1);
videoRenderer.IsSync = false; // Disable A/V sync for lowest latency

pipeline.Connect(rtspSource.VideoOutput, videoRenderer.Input);
```

For detailed buffer tuning and UDP vs TCP transport configuration, see the [RTSP Protocol Configuration](../../../videocapture/video-sources/ip-cameras/rtsp/) reference.

## Camera Time per Frame

To stamp every frame with the camera's own clock - for example to draw one uniform timestamp overlay across cameras of different brands - enable `AddReferenceTimestampMeta`. Each frame from a sample grabber or a buffer sink then carries the camera's NTP time in `SenderNTPTime`:

```
rtspSettings.AddReferenceTimestampMeta = true;

// Between the source and the renderer
var grabber = new VideoSampleGrabberBlock();
grabber.OnVideoFrameBuffer += (s, e) =>
{
    DateTime? cameraTime = e.Frame.SenderNTPTime; // UTC, null without Sender Reports
};

pipeline.Connect(rtspSource.VideoOutput, grabber.Input);
pipeline.Connect(grabber.Output, videoRenderer.Input);
```

The time comes from the camera's RTCP Sender Reports, so it depends on the camera: it is `null` until the first report arrives, and for the whole session when the camera sends none or the reports are blocked (with UDP transport, try `AllowedProtocols = RTSPSourceProtocol.TCP`). The SDK logs one warning when no report arrives within 10 seconds. A `VideoMixerBlock` creates new frames, so read the time before the mixer. `FallbackSwitchSourceBlock` does not carry it - use `RTSPSourceBlock`.

## Recording Options

There are two approaches to recording RTSP streams, each suited for different use cases:

|  | Passthrough (No Re-encoding) | Re-encoding |
| --- | --- | --- |
| CPU usage | Minimal | High |
| Video quality | Original (lossless) | Re-compressed |
| File size | Same as source | Configurable bitrate |
| Video processing | No overlays, resize, or effects | Full editing capability |
| Best for | Surveillance archival, NVR | Streaming, post-processing |

### Recording with Passthrough (No Re-encoding)

Passthrough recording saves the original compressed stream directly to a file without decoding or re-encoding the video. This approach uses `RTSPRAWSourceBlock` instead of `RTSPSourceBlock` — the video data passes straight from the camera to the file sink with zero CPU overhead for video processing.

```
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Special;
using VisioForge.Core.MediaBlocks.AudioEncoders;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.AudioEncoders;
using VisioForge.Core.Types.X.Sources;

// Create a separate pipeline for recording
var recordPipeline = new MediaBlocksPipeline();

// Create RAW RTSP source (receives compressed stream directly)
var rawSettings = await RTSPRAWSourceSettings.CreateAsync(
    new Uri("rtsp://192.168.1.21:554/stream"),
    "admin", "password", true);

var rawSource = new RTSPRAWSourceBlock(rawSettings);

// Create MP4 file sink
var muxer = new MP4SinkBlock(new MP4SinkSettings("output.mp4"));

// Connect video — no decoding, no re-encoding
var videoPad = (muxer as IMediaBlockDynamicInputs)
    .CreateNewInput(MediaBlockPadMediaType.Video);
recordPipeline.Connect(rawSource.VideoOutput, videoPad);

// Connect audio — re-encode to AAC for MP4 compatibility
var audioPad = (muxer as IMediaBlockDynamicInputs)
    .CreateNewInput(MediaBlockPadMediaType.Audio);

var decodeBin = new DecodeBinBlock(false, true, false);
var aacEncoder = new AACEncoderBlock(new AVENCAACEncoderSettings());

recordPipeline.Connect(rawSource.AudioOutput, decodeBin.Input);
recordPipeline.Connect(decodeBin.AudioOutput, aacEncoder.Input);
recordPipeline.Connect(aacEncoder.Output, audioPad);

await recordPipeline.StartAsync();
```

**Container format choice:** Use MP4 for broad playback compatibility. Use MPEG-TS (`MPEGTSSinkBlock`) for crash-safe recording — if the process terminates unexpectedly, all data written up to that point is preserved. MPEG-TS is preferred for 24/7 surveillance recording.

For a complete implementation with error handling, state management, and resource cleanup, see the [Save RTSP Stream Without Re-encoding](../rtsp-save-original-stream/) guide.

### Recording with Re-encoding

When you need to resize the video, add overlays or watermarks, change the codec, or reduce the bitrate, use `RTSPSourceBlock` (which decodes the stream) followed by encoder blocks:

```
// RTSPSourceBlock decodes the stream, allowing processing
var rtspSource = new RTSPSourceBlock(rtspSettings);
var mp4Sink = new MP4SinkBlock("output.mp4");

// Video: decoded → (optional processing) → encode to H.264 → mux
// Audio: decoded → encode to AAC → mux

pipeline.Connect(rtspSource.VideoOutput, /* encoder/processing blocks */);
```

For detailed code examples of recording with video processing (resize, effects, face detection), see the [ONVIF Capture with Postprocessing](../onvif-capture-with-postprocessing/) guide. For a simpler re-encoding example, see the [IP Camera Capture to MP4](../../../videocapture/video-tutorials/ip-camera-capture-mp4/) tutorial.

## Frequently Asked Questions

### How do I authenticate with an RTSP IP camera in C#?

Embed credentials directly in the RTSP URL (`rtsp://user:pass@ip:554/path`) or pass them as separate parameters to `RTSPSourceSettings.CreateAsync()`. For ONVIF cameras, connect via `ONVIFClientX` first with username and password, then retrieve the authenticated stream URI using `GetStreamUriAsync()`. Most cameras support digest authentication by default.

### Should I use passthrough or re-encoding when recording RTSP streams?

Use passthrough for surveillance archival and NVR applications — it requires zero CPU for video processing and preserves the original camera quality. Use re-encoding when you need to resize, add overlays, change codec or bitrate, or stream to a different format. Most professional recording applications use passthrough to minimize server load.

### How do I reduce RTSP stream latency below 100ms?

Enable `LowLatencyMode = true` on `RTSPSourceSettings` (150ms jitter buffer vs the default 500ms). For even lower delay, set `Latency` to 150ms or less and disable video renderer sync with `IsSync = false`. Use UDP transport when your network supports it. See the [RTSP protocol guide](../../../videocapture/video-sources/ip-cameras/rtsp/) for advanced buffer tuning options.

### Preview works in VLC but freezes or ends after about a minute?

The default protocol list tries UDP first. Force TCP, and if the camera still drops the session, enable `ForceCustomKeepAlive` so the source sends GET\_PARAMETER every 30 seconds:

```
rtspSettings.AllowedProtocols = RTSPSourceProtocol.TCP;
rtspSettings.ForceCustomKeepAlive = true;
```

### Can I view and record from multiple IP cameras simultaneously?

Yes. Create separate `MediaBlocksPipeline` instances for each camera — each pipeline runs independently with its own RTSP connection, decoder, and renderer. You can add per-camera recording by creating additional recording pipelines using `RTSPRAWSourceBlock` for passthrough capture. The RTSP MultiView Demo on GitHub shows a complete implementation with grid layout and individual record controls.

### Which container format should I use for passthrough recording — MP4 or MPEG-TS?

Use MP4 for standard playback compatibility across devices and players. Use MPEG-TS for crash-safe recording — if the application or system crashes during recording, all data written up to the failure point is preserved. For 24/7 surveillance or mission-critical recording, MPEG-TS is the recommended choice.

## Overview

This guide demonstrates how to save an RTSP stream to an MP4 file by capturing the original video stream from an RTSP IP camera without re-encoding the video. This approach is highly beneficial for preserving the original video quality from cameras and minimizing CPU usage when you need to record footage. The audio stream can be passed through or, optionally, re-encoded for better compatibility, allowing you to save the complete streaming data. Tools like FFmpeg and VLC offer command-line or UI-based methods to record an RTSP stream; however, this guide focuses on a programmatic approach using the VisioForge Media Blocks SDK for .NET developers who need to create applications that connect to and record video from RTSP cameras.

## Code Sample: RTSPRecorder Class

The following C# code defines an `RTSPRecorder` class that encapsulates the logic for capturing and saving the RTSP stream.

```
using System;
using System.Threading.Tasks;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.AudioEncoders;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.Special;
using VisioForge.Core.Types.Events;
using VisioForge.Core.Types.X.AudioEncoders;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.Sources;

namespace RTSPCaptureOriginalStream
{
    /// <summary>
    /// RTSPRecorder class encapsulates the RTSP recording functionality to save RTSP stream to file.
    /// It uses the Media Blocks SDK to create a pipeline that connects an
    /// RTSP source (like an IP camera) to an MP4 sink (file).
    /// </summary>
    public class RTSPRecorder : IAsyncDisposable
    {
        /// <summary>
        /// The MediaBlocks pipeline that manages the flow of media data.
        /// </summary>
        public MediaBlocksPipeline Pipeline { get; private set; }

        // Private fields for the MediaBlock components
        private MediaBlock _muxer;               // MP4 container muxer (sink)
        private RTSPRAWSourceBlock _rtspRawSource; // RTSP stream source (provides raw streams)
        private DecodeBinBlock _decodeBin;       // Optional: Audio decoder (if re-encoding audio)
        private AACEncoderBlock _audioEncoder;   // Optional: AAC audio encoder (if re-encoding audio)
        private bool disposedValue;              // Flag to prevent multiple disposals

        /// <summary>
        /// Event fired when an error occurs in the pipeline.
        /// </summary>
        public event EventHandler<ErrorsEventArgs> OnError;

        /// <summary>
        /// Event fired when a status message is available.
        /// </summary>
        public event EventHandler<string> OnStatusMessage;

        /// <summary>
        /// Output filename for the MP4 recording.
        /// </summary>
        public string Filename { get; set; } = "output.mp4";

        /// <summary>
        /// Whether to re-encode audio to AAC format (recommended for compatibility).
        /// If false, audio is passed through.
        /// </summary>
        public bool ReencodeAudio { get; set; } = true;

        /// <summary>
        /// Starts the recording session by creating and configuring the MediaBlocks pipeline.
        /// </summary>
        /// <param name="rtspSettings">RTSP source configuration settings.</param>
        /// <returns>True if the pipeline started successfully, false otherwise.</returns>
        public async Task<bool> StartAsync(RTSPRAWSourceSettings rtspSettings)
        {
            // Create a new MediaBlocks pipeline
            Pipeline = new MediaBlocksPipeline();
            Pipeline.OnError += (sender, e) => OnError?.Invoke(this, e); // Bubble up errors

            OnStatusMessage?.Invoke(this, "Creating pipeline to record RTSP stream...");

            // 1. Create the RTSP source block.
            // RTSPRAWSourceBlock provides raw, un-decoded elementary streams (video and audio) from your IP camera or other RTSP cameras.
            _rtspRawSource = new RTSPRAWSourceBlock(rtspSettings);

            // 2. Create the MP4 sink (muxer) block.
            // This block will write the media streams into an MP4 file.
            _muxer = new MP4SinkBlock(new MP4SinkSettings(Filename));

            // 3. Connect Video Stream (Passthrough)
            // Create a dynamic input pad on the muxer for the video stream.
            // We connect the raw video output from the RTSP source directly to the MP4 sink.
            // This ensures the video is not re-encoded when you record the camera feed.
            var inputVideoPad = (_muxer as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Video);
            Pipeline.Connect(_rtspRawSource.VideoOutput, inputVideoPad);
            OnStatusMessage?.Invoke(this, "Video stream connected (passthrough for original quality video).");

            // 4. Connect Audio Stream (Optional Re-encoding)
            // This section handles how the audio from the RTSP stream is processed and saved to the file.
            if (rtspSettings.AudioEnabled)
            {
                // Create a dynamic input pad on the muxer for the audio stream.
                var inputAudioPad = (_muxer as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Audio);

                if (ReencodeAudio)
                {
                    // If audio re-encoding is enabled (e.g., to AAC for compatibility):
                    OnStatusMessage?.Invoke(this, "Setting up audio re-encoding to AAC for the recording...");

                    // Create a decoder block that only handles audio.
                    // We need to decode the original audio before re-encoding it to save the MP4 stream with compatible audio.
                    _decodeBin = new DecodeBinBlock(renderVideo: false, renderAudio: true, renderSubtitle: false)
                    {
                         // We can disable the internal audio converter if we're sure about the format
                         // or if the encoder handles conversion. For AAC, it's generally fine.
                         DisableAudioConverter = true
                    };

                    // Create an AAC encoder with default settings.
                    _audioEncoder = new AACEncoderBlock(new AVENCAACEncoderSettings());

                    // Connect the audio processing pipeline:
                    // RTSP audio output -> Decoder -> AAC Encoder -> MP4 Sink audio input
                    Pipeline.Connect(_rtspRawSource.AudioOutput, _decodeBin.Input);
                    Pipeline.Connect(_decodeBin.AudioOutput, _audioEncoder.Input);
                    Pipeline.Connect(_audioEncoder.Output, inputAudioPad);
                    OnStatusMessage?.Invoke(this, "Audio stream connected (re-encoding to AAC for MP4 file).");
                }
                else
                {
                    // If audio re-encoding is disabled, connect RTSP audio directly to the muxer.
                    // Note: This may cause issues if the original audio format is not
                    // compatible with the MP4 container (e.g., G.711 PCMU/PCMA) when trying to save the RTSP stream.
                    // Common compatible formats include AAC. Check your camera's audio format.
                    Pipeline.Connect(_rtspRawSource.AudioOutput, inputAudioPad);
                    OnStatusMessage?.Invoke(this, "Audio stream connected (passthrough). Warning: Compatibility depends on original camera audio format for the file.");
                }
            }

            // 5. Start the pipeline to record video
            OnStatusMessage?.Invoke(this, "Starting recording pipeline to save RTSP stream to file...");
            bool success = await Pipeline.StartAsync();
            if (success)
            {
                OnStatusMessage?.Invoke(this, "Recording pipeline started successfully.");
            }
            else
            {
                OnStatusMessage?.Invoke(this, "Failed to start recording pipeline.");
            }
            return success;
        }

        /// <summary>
        /// Stops the recording by stopping the MediaBlocks pipeline.
        /// </summary>
        /// <returns>True if the pipeline stopped successfully, false otherwise.</returns>
        public async Task<bool> StopAsync()
        {
            if (Pipeline == null)
                return false;

            OnStatusMessage?.Invoke(this, "Stopping recording pipeline...");
            bool success = await Pipeline.StopAsync();
            if (success)
            {
                OnStatusMessage?.Invoke(this, "Recording pipeline stopped successfully.");
            }
            else
            {
                OnStatusMessage?.Invoke(this, "Failed to stop recording pipeline.");
            }

            // Detach the error handler to prevent issues if StopAsync is called multiple times
            // or before DisposeAsync
            if (Pipeline != null)
            {
                 Pipeline.OnError -= OnError;
            }

            return success;
        }

        /// <summary>
        /// Asynchronously disposes of the RTSPRecorder and all its resources.
        /// Implements the IAsyncDisposable pattern for proper resource cleanup.
        /// </summary>
        public async ValueTask DisposeAsync()
        {
            if (!disposedValue)
            {
                if (Pipeline != null)
                {
                    Pipeline.OnError -= (sender, e) => OnError?.Invoke(this, e); // Ensure detachment
                    await Pipeline.DisposeAsync();
                    Pipeline = null;
                }

                // Dispose of all MediaBlock components
                // Using 'as IDisposable' for safe casting and disposal.
                (_muxer as IDisposable)?.Dispose();
                _muxer = null;

                _rtspRawSource?.Dispose();
                _rtspRawSource = null;

                _decodeBin?.Dispose();
                _decodeBin = null;

                _audioEncoder?.Dispose();
                _audioEncoder = null;

                disposedValue = true;
            }
        }
    }
}
```

## Explanation of the Code

1. **`RTSPRecorder` Class**: This class is central to helping a user save RTSP stream to file.

   - Implements `IAsyncDisposable` for proper resource management.
   - `Pipeline`: The `MediaBlocksPipeline` object that orchestrates the media flow.
   - `_rtspRawSource`: An `RTSPRAWSourceBlock` is used. The "RAW" is key here, as it provides the elementary streams (video and audio) from camera without attempting to decode them initially.
   - `_muxer`: An `MP4SinkBlock` is used to write the incoming video and audio streams into an MP4 file.
   - `_decodeBin` and `_audioEncoder`: These are optional blocks used only if `ReencodeAudio` is true. `_decodeBin` decodes the original audio from the IP camera, and `_audioEncoder` (e.g., `AACEncoderBlock`) re-encodes it to a more compatible format like AAC.
   - `Filename`: Specifies the output MP4 file path where the video will be saved.
   - `ReencodeAudio`: A boolean property to control audio processing. If `true`, audio is re-encoded to AAC. If `false`, audio is passed through directly. Check your camera audio format for compatibility if set to false.
2. **`StartAsync(RTSPRAWSourceSettings rtspSettings)` Method**: This method initiates the process to **record RTSP stream**.

   - Initializes `MediaBlocksPipeline`.
   - **RTSP Source**: Creates `_rtspRawSource` with `RTSPRAWSourceSettings`. These settings include the URL (the path to your camera's stream), credentials for user access, and audio capture settings.
   - **MP4 Sink**: Creates `_muxer` (MP4 sink) with the target filename.
   - **Video Path (Passthrough)**:
     - A new dynamic input pad for video is created on the `_muxer`.
     - `Pipeline.Connect(_rtspRawSource.VideoOutput, inputVideoPad);` This line directly connects the raw video output from the RTSP source to the MP4 muxer's\*video input. No re-encoding occurs for the video stream.
   - **Audio Path (Conditional)**: Determines how audio from the **camera** is handled when you **save to file**.
     - If `rtspSettings.AudioEnabled` is true:
       - A new dynamic input pad for audio is created on the `_muxer`.
       - If `ReencodeAudio` is `true` (recommended for wider file compatibility):
         - `_decodeBin` is created to decode the incoming audio from the camera. It's configured to only process audio (`new DecodeBinBlock(renderVideo: false)`).
         - `_audioEncoder` (e.g., `AACEncoderBlock`) is created.
         - The pipeline is connected: `_rtspRawSource.AudioOutput` -> `_decodeBin.Input` -> `_decodeBin.AudioOutput` -> `_audioEncoder.Input` -> `_audioEncoder.Output` -> `inputAudioPad` (muxer's audio input).
       - If `ReencodeAudio` is `false`:
         - `Pipeline.Connect(_rtspRawSource.AudioOutput, inputAudioPad);` The raw audio output from the camera source is connected directly to the MP4 muxer. *Caution*: This relies on the original audio codec from the camera being compatible with the MP4 container (e.g., AAC). Formats like G.711 (PCMU/PCMA) are common in RTSP cameras but are not standard in MP4 and might lead to playback issues or require specialized players if you save this way. Check your camera's documentation.
   - Starts the pipeline using `Pipeline.StartAsync()` to begin the streaming video record process.
3. **`StopAsync()` Method**: Stops the `Pipeline`.
4. **`DisposeAsync()` Method**:

   - Cleans up all resources, including the pipeline and individual media blocks.

## Key Considerations

Re-encoding to AAC is generally safer for wider compatibility.

- **Error Handling**: Robust applications should implement thorough error handling by subscribing to the `OnError` event of the `RTSPRecorder` (or directly from the `MediaBlocksPipeline`).
- **Resource Management**: Always `DisposeAsync` the `RTSPRecorder` instance (and thus the `MediaBlocksPipeline`) when done to free up resources. `VisioForgeX.DestroySDK()` should be called once when your application exits.

**Tags:** Media Blocks SDK, .NET, MPEG-TS, HLS, SCTE-35, SRT, UDP, RIST, Ad insertion, C#
**API:** MPEGTSDemuxBlock, UniversalSourceBlock, MPEGTSSinkBlock, UDPMPEGTSSinkBlock, SRTMPEGTSSinkBlock, RISTMPEGTSSinkBlock, VideoCaptureCoreX, SpliceEventArgs

# SCTE-35 Ad Markers in MPEG-TS and HLS with C# .NET

[Media Blocks SDK .NET](https://www.visioforge.com/media-blocks-sdk-net)

## Overview

SCTE-35 splice sections mark the points where a broadcast or FAST channel leaves the network feed for an ad break and comes back. They travel in the transport stream on a PID of their own (stream type 0x86). The Media Blocks SDK .NET lets you:

1. **Read** them from an MPEG-TS file or stream (`MPEGTSDemuxBlock`), or from an MPEG-TS or HLS source decoded by `UniversalSourceBlock`, as an `OnSpliceEvent` event.
2. **Keep** them through a remux: a TS read with SCTE-35 enabled and written by `MPEGTSSinkBlock` with a SCTE-35 PID carries the same splice commands in its output.
3. **Insert** your own splice\_insert commands into an MPEG-TS file, or into an MPEG-TS stream sent over UDP, SRT or RIST - from a Media Blocks pipeline or from `VideoCaptureCoreX`.

SCTE-35 is off by default: without `EnableSCTE35` the demuxer drops the SCTE-35 PID.

## Read splice events from MPEG-TS

```
var pipeline = new MediaBlocksPipeline();

var source = new BasicFileSourceBlock("channel.ts");

var demux = new MPEGTSDemuxBlock(renderVideo: true, renderAudio: true);
demux.Settings.EnableSCTE35 = true;
demux.OnSpliceEvent += (sender, e) =>
{
    if (e.CommandType == SpliceCommandType.Insert)
    {
        var kind = e.OutOfNetwork ? "break starts" : "break ends";
        Console.WriteLine($"Event {e.EventId}: {kind} at {e.RunningTime}, duration {e.BreakDuration}");
    }
};

pipeline.Connect(source.Output, demux.Input);
// Connect demux.VideoOutput and demux.AudioOutput to renderers, encoders or sinks.

await pipeline.StartAsync();
```

`SpliceEventArgs` carries:

| Property | Meaning |
| --- | --- |
| `Section` | The whole splice\_info\_section, from table\_id (0xFC) to CRC\_32. Use it for descriptors (segmentation, avail) and for commands other than splice\_insert and time\_signal. |
| `CommandType` | `Insert` (splice\_insert), `TimeSignal`, `Null`, `Schedule`, `BandwidthReservation` or `Private`. |
| `EventId`, `Cancel`, `OutOfNetwork`, `Immediate` | The splice\_insert fields. `OutOfNetwork = true` starts a break, `false` ends it. |
| `PtsTime` | The splice time in the stream's 90 kHz PTS clock, pts\_adjustment applied. |
| `RunningTime` | The same point as pipeline running time - the time base of the buffers coming out of the demuxer. Where the stream's timestamps jump, the demuxer closes the gap, and `RunningTime` follows its output, not the raw PTS. `null` when the demuxer cannot map it: the section arrives before the stream's clock is known, or the point lies before the start of the output. |
| `BreakDuration`, `AutoReturn` | The break\_duration of a splice\_insert. |
| `Encrypted`, `PtsAdjustment` | When `Encrypted` is set, only `Section` and `PtsAdjustment` are filled in. |

The event is raised on a streaming thread as the demuxer reaches the section, usually a few seconds before the splice point itself. Return quickly; hand the work to your own thread or the UI dispatcher.

## Read splice events from HLS

`UniversalSourceBlock` raises the same event for an MPEG-TS source and for an HLS stream of MPEG-TS segments. The sections reach the application after passing the decoders:

```
var settings = await UniversalSourceSettings.CreateAsync(new Uri("https://example.com/live/index.m3u8"));
settings.EnableSCTE35 = true;

var source = new UniversalSourceBlock(settings);
source.OnSpliceEvent += (sender, e) => Console.WriteLine($"{e.CommandType} {e.EventId} at {e.RunningTime}");
```

The SCTE-35 sections inside the TS segments are what is read. Playlist cue tags (`#EXT-X-CUE-OUT`, `#EXT-X-DATERANGE`) are not.

## Keep splice events through a remux

Set `EnableSCTE35` on the demuxer and `SCTE35PID` on the sink. Each section travels with the streams, and the muxer writes it on the new PID with its timing adjusted to the output:

```
var demux = new MPEGTSDemuxBlock(renderVideo: true, renderAudio: true);
demux.Settings.EnableSCTE35 = true;
pipeline.Connect(source.Output, demux.Input);

var videoParse = new H264ParseBlock();
pipeline.Connect(demux.VideoOutput, videoParse.Input);

var sink = new MPEGTSSinkBlock(new MPEGTSSinkSettings("output.ts") { SCTE35PID = 500 });
pipeline.Connect(videoParse.Output, sink.CreateNewInput(MediaBlockPadMediaType.Video));
```

## Insert splice events into MPEG-TS output

With `SCTE35PID` set, `MPEGTSSinkBlock` writes a SCTE-35 stream with a splice\_null heartbeat every 5 minutes, and `InsertSpliceOut` / `InsertSpliceIn` add splice\_insert commands while the pipeline runs:

```
var sink = new MPEGTSSinkBlock(new MPEGTSSinkSettings("channel.ts") { SCTE35PID = 500 });
pipeline.Connect(h264Encoder.Output, sink.CreateNewInput(MediaBlockPadMediaType.Video));

await pipeline.StartAsync();

// A 30-second break starting at 10 s of pipeline running time, announced ahead of time.
sink.InsertSpliceOut(eventId: 1, spliceTime: TimeSpan.FromSeconds(10), duration: TimeSpan.FromSeconds(30));
// Wait until about 5 s before the break ends, then announce the return.
await Task.Delay(TimeSpan.FromSeconds(35));
sink.InsertSpliceIn(eventId: 1, spliceTime: TimeSpan.FromSeconds(40));
```

- Times are pipeline running time. Pass `null` for an immediate splice.
- Announce a splice a few seconds before it happens (SCTE 67 recommends at least 4 seconds). The muxer converts the time to the output's PTS and asks the encoder for a key frame at the splice point.
- Send each splice a few seconds before its own point, not the whole break at once. The muxer keeps one pending section until its next packet: a second call before then replaces the first, and both return `true`.
- Use a PID from 0x50 to 0x1FFE that no other stream in the output uses (500 in the samples). Lower PIDs are taken by the tables and by the muxer's own streams; a PID outside that range is reported through `OnError`. A clash with another stream inside the range is not detected.

## Insert splice events into a UDP, SRT or RIST stream

The network MPEG-TS sinks take the same `SCTE35PID` setting and the same `InsertSpliceOut` / `InsertSpliceIn` methods as `MPEGTSSinkBlock`. Use them when the channel goes out live - to a headend, a cloud packager or an ad-insertion server that reads SCTE-35 from the transport stream - rather than into a file.

| Sink block | Settings class carrying `SCTE35PID` |
| --- | --- |
| `UDPMPEGTSSinkBlock` | `UDPSinkSettings` |
| `MultiUDPMPEGTSSinkBlock` | `MultiUDPSinkSettings` |
| `SRTMPEGTSSinkBlock` | `SRTSinkSettings` |
| `RISTMPEGTSSinkBlock` | `RISTSinkSettings` |

```
var pipeline = new MediaBlocksPipeline();

var video = new VirtualVideoSourceBlock(new VirtualVideoSourceSettings());
var encoder = new H264EncoderBlock(new OpenH264EncoderSettings());
pipeline.Connect(video.Output, encoder.Input);

var srt = new SRTMPEGTSSinkBlock(new SRTSinkSettings
{
    Uri = "srt://ingest.example.com:9000",
    Mode = SRTConnectionMode.Caller,
    SCTE35PID = 500,
});
pipeline.Connect(encoder.Output, srt.CreateNewInput(MediaBlockPadMediaType.Video));

await pipeline.StartAsync();

// A 30-second break at 60 s of running time, announced 5 seconds ahead.
await Task.Delay(TimeSpan.FromSeconds(55));
srt.InsertSpliceOut(eventId: 7, spliceTime: TimeSpan.FromSeconds(60), duration: TimeSpan.FromSeconds(30));

// The return, announced near the end of the break.
await Task.Delay(TimeSpan.FromSeconds(30));
srt.InsertSpliceIn(eventId: 7, spliceTime: TimeSpan.FromSeconds(90));
```

The rules of the previous section apply unchanged: running-time splice points, a few seconds of notice, and one pending section in the muxer. Set `SCTE35PID` before the pipeline starts - a PID set later never reaches the muxer, and the insert methods return `false`. Splices read by an upstream `MPEGTSDemuxBlock` with `EnableSCTE35` pass through these sinks too, as they do through `MPEGTSSinkBlock`.

A file input needs no pacing. When the input is not live, the UDP, multi-destination UDP and SRT MPEG-TS sinks send each packet at its timestamp, so a file goes out in real time and the sink drops nothing; a stalled SRT connection holds the file back until it recovers. With a live source they send each packet as it arrives, and drop the oldest ones if the network stalls, so the rest of the pipeline - a preview, a recording - keeps running. The input counts as live when any of its sources is live. A push source is live when `IsLive` is set on its settings: `PushVideoSourceSettings`, `PushAudioSourceSettings` and `PushJPEGSourceSettings` default to `true`, `PushDataSourceSettings` to `false`.

`UDPSinkBlock`, `MultiUDPSinkBlock` and `SRTSinkBlock` send an already-muxed stream unchanged and ignore `SCTE35PID`.

## Insert splice events from Video Capture SDK .NET

`VideoCaptureCoreX` builds its `SRTOutput`, `RISTOutput` and `MPEGTSOutput` on the same sinks. Set the PID on the output's `Sink` settings, and insert by the output's index:

```
var capture = new VideoCaptureCoreX(videoView);
capture.Video_Source = videoSourceSettings;

var srt = new SRTOutput("srt://ingest.example.com:9000");
srt.Video = new OpenH264EncoderSettings();
srt.Sink.SCTE35PID = 500;
capture.Outputs_Add(srt);

await capture.StartAsync();

// Index 0: the first output added. Times are the output's running time - the clock Outputs_GetDuration reports.
capture.Outputs_InsertSpliceOut(0, eventId: 7, spliceTime: TimeSpan.FromSeconds(60), duration: TimeSpan.FromSeconds(30));
// ... near the end of the break:
capture.Outputs_InsertSpliceIn(0, eventId: 7, spliceTime: TimeSpan.FromSeconds(90));
```

Both methods return `false` and raise `OnError` when the output has not started or was stopped, was started without a PID, or is not an MPEG-TS output - one of these three, or a `CustomBlocksOutputSettings` whose `Sink` is any MPEG-TS sink block, `UDPMPEGTSSinkBlock` and `MultiUDPMPEGTSSinkBlock` included.

## Platforms

Reading and inserting - into files and into UDP, SRT and RIST streams - work on Windows, macOS, Linux and iOS, wherever the sink block itself is available (`IsAvailable()`). Android is not supported: its GStreamer build does not export the MPEG-TS section library, so `OnSpliceEvent` never fires there (the pipeline reports one error when the first section arrives) and the insert methods return `false` with an error in the log.

SCTE-104 (the SDI/VANC form of these markers) is not covered by this API.

## Overview

This guide shows how to receive a UDP MPEG-TS stream and write it to a file **without re-encoding** the video or audio. Many encoders, hardware appliances, and broadcast contribution feeds push H.264 or H.265 video together with AAC audio over UDP inside an MPEG transport stream. When you only need to record that feed, decoding and re-encoding it wastes CPU and degrades quality. **Remuxing** — also called stream copy or passthrough capture — moves the already-compressed packets straight into a new container, so the recording is bit-for-bit identical to what arrived on the wire.

The VisioForge Media Blocks SDK makes this a short pipeline: a `UDPRAWSourceBlock` listens on a UDP port, demultiplexes the transport stream, and exposes the encoded elementary streams on its output pads. You connect those pads directly to an MP4 or MPEG-TS sink, and the SDK muxes the data to disk. No decoder, no encoder, minimal CPU.

This is the UDP counterpart of the [Save RTSP Stream Without Re-encoding](../rtsp-save-original-stream/) guide; the recording concept is the same, only the network source differs.

## Core Features

- **Zero re-encoding**: video and audio are copied straight to the container, preserving the original quality.
- **Low CPU usage**: no decode/encode stages, suitable for embedded devices and many simultaneous recorders.
- **H.264 and H.265 video** plus **AAC audio** passthrough into MP4 or MPEG-TS.
- **Unicast and multicast** UDP input via a simple `udp://host:port` URI.
- **File splitting** for continuous, long-running capture with size-bounded segments.
- **Optional live preview** alongside the recording.

## Core Concept

A UDP MPEG-TS feed carries one or more elementary streams (encoded video, encoded audio) packetized into the transport stream. To record it without re-encoding, the pipeline only needs to:

1. Receive the UDP packets and parse the MPEG-TS container.
2. Pick out the encoded video and audio elementary streams.
3. Stamp each buffer with a valid presentation timestamp (PTS) — strict muxers such as `mp4mux` reject buffers without one.
4. Mux the encoded streams into the target container.

`UDPRAWSourceBlock` performs steps 1–3 for you. In `Auto`/`MPEGTS` mode it runs the transport stream through a parser chain (`h264parse`/`h265parse` for video, `aacparse` for audio) that infers and interpolates timestamps, so the buffers leaving the source are already mux-ready. You only wire the source to a sink:

```
graph LR;
    UDPRAWSourceBlock-- "encoded H.264/H.265" -->MP4SinkBlock;
    UDPRAWSourceBlock-- "encoded AAC" -->MP4SinkBlock;
```

## Code Sample: UDPRemuxRecorder Class

The `UDPRemuxRecorder` class below encapsulates the whole pipeline. It receives a UDP MPEG-TS stream and remuxes it to an MP4 file, with optional audio passthrough.

```
using System;
using System.Threading.Tasks;
using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.Types.Events;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.Sources;

namespace UDPCaptureSample
{
    /// <summary>
    /// Records a UDP MPEG-TS stream (H.264/HEVC + AAC) to an MP4 file without re-encoding.
    /// The encoded elementary streams are remuxed straight into the container.
    /// </summary>
    public class UDPRemuxRecorder : IAsyncDisposable
    {
        private MediaBlocksPipeline _pipeline;
        private UDPRAWSourceBlock _source;
        private MP4SinkBlock _sink;

        /// <summary>
        /// Raised when the underlying pipeline reports an error.
        /// </summary>
        public event EventHandler<ErrorsEventArgs> OnError;

        /// <summary>
        /// Builds the recording pipeline.
        /// </summary>
        /// <param name="udpUrl">UDP source URL, e.g. "udp://0.0.0.0:1234" or "udp://239.1.1.1:1234".</param>
        /// <param name="outputFile">Destination MP4 file path.</param>
        /// <param name="recordAudio">Capture the AAC audio track in addition to video.</param>
        public async Task BuildAsync(string udpUrl, string outputFile, bool recordAudio = true)
        {
            // Initialize the SDK once. InitSDKAsync() is idempotent, so a second
            // recorder calling it again is a safe no-op. In a larger app you can
            // instead call it a single time at startup.
            await VisioForgeX.InitSDKAsync();

            _pipeline = new MediaBlocksPipeline();
            _pipeline.OnError += (sender, e) => OnError?.Invoke(this, e);

            // 1. UDP MPEG-TS source. Auto mode detects the container and exposes the
            //    encoded elementary streams (no decoding). AudioEnabled adds the AAC pad.
            var settings = new UDPRAWSourceSettings(new Uri(udpUrl))
            {
                Mode = UDPRAWSourceMode.Auto,
                AudioEnabled = recordAudio
            };

            _source = new UDPRAWSourceBlock(settings);

            // 2. MP4 sink. Each track gets its own dynamic input pad.
            _sink = new MP4SinkBlock(new MP4SinkSettings(outputFile));

            // 3. Connect the encoded video stream directly to the muxer (passthrough).
            var videoInput = (_sink as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Video);
            _pipeline.Connect(_source.VideoOutput, videoInput);

            // 4. Connect the encoded audio stream, if present. AudioOutput is non-null
            //    only when AudioEnabled is true and the stream actually carries audio.
            if (recordAudio && _source.AudioOutput != null)
            {
                var audioInput = (_sink as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Audio);
                _pipeline.Connect(_source.AudioOutput, audioInput);
            }
        }

        /// <summary>
        /// Starts recording. Returns false if the pipeline failed to start.
        /// </summary>
        public Task<bool> StartAsync() => _pipeline?.StartAsync() ?? Task.FromResult(false);

        /// <summary>
        /// Stops recording and finalizes the output file.
        /// </summary>
        public async Task StopAsync()
        {
            if (_pipeline != null)
            {
                await _pipeline.StopAsync();
            }
        }

        /// <inheritdoc/>
        public async ValueTask DisposeAsync()
        {
            if (_pipeline != null)
            {
                await _pipeline.DisposeAsync();
                _pipeline = null;
            }

            _sink = null;
            _source = null;
        }
    }
}
```

## Explanation of the Code

- **`VisioForgeX.InitSDKAsync()`** initializes the SDK once per process. Call `VisioForgeX.DestroySDK()` when your application exits.
- **`UDPRAWSourceSettings`** takes the listening URL. `Mode = UDPRAWSourceMode.Auto` lets the source detect the MPEG-TS container and expose the encoded streams; `UDPRAWSourceMode.MPEGTS` forces the same behavior explicitly. Setting `AudioEnabled = true` tells the source to expose the audio elementary stream on `AudioOutput`.
- **`_source.VideoOutput`** always carries the encoded video (H.264 or H.265) — no decoding happens. **`_source.AudioOutput`** is non-null only when `AudioEnabled` is `true` and the mode is `Auto`/`MPEGTS`; it carries the encoded AAC audio.
- **`MP4SinkBlock` implements `IMediaBlockDynamicInputs`**, so you call `CreateNewInput(MediaBlockPadMediaType.Video)` / `CreateNewInput(MediaBlockPadMediaType.Audio)` to add one input pad per track, then connect the matching source pad.
- **Timestamps**: in `Auto`/`MPEGTS` mode the source inserts `h264parse`/`h265parse`/`aacparse` with timestamp inference and interpolation, so every buffer reaching the MP4 muxer has a valid PTS. This is why the remuxed file has correct timing without any decode step.
- **`StartAsync()`** returns `Task<bool>` — check the result and tear down on `false`.

## How to Use the UDPRemuxRecorder

```
await using var recorder = new UDPRemuxRecorder();
recorder.OnError += (s, e) => Console.WriteLine($"Pipeline error: {e.Message}");

await recorder.BuildAsync("udp://0.0.0.0:1234", "output.mp4", recordAudio: true);

if (await recorder.StartAsync())
{
    Console.WriteLine("Recording... press any key to stop.");
    Console.ReadKey(true);
    await recorder.StopAsync();
    Console.WriteLine("Saved output.mp4");
}
else
{
    Console.WriteLine("Failed to start. Check the UDP URL and port.");
}

VisioForgeX.DestroySDK();
```

The URL is the **local listening endpoint**, not the sender's address:

- `udp://0.0.0.0:1234` — listen on all interfaces, port 1234 (unicast).
- `udp://239.1.1.1:1234` — join the multicast group `239.1.1.1` on port 1234 (the source joins the group automatically).
- `udp://192.168.1.10:1234` — bind to a specific local interface.

## Recording to MPEG-TS Instead of MP4

To keep the recording in an MPEG-TS container (`.ts`) — which tolerates a wider range of codecs and is robust to truncation — swap the sink for an `MPEGTSSinkBlock`. The source and connection logic are identical:

```
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.Types.X.Sinks;

var sink = new MPEGTSSinkBlock(new MPEGTSSinkSettings("output.ts"));

var videoInput = (sink as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Video);
pipeline.Connect(source.VideoOutput, videoInput);

if (source.AudioOutput != null)
{
    var audioInput = (sink as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Audio);
    pipeline.Connect(source.AudioOutput, audioInput);
}
```

## Splitting the Recording into Files

For continuous, long-running capture, split the output into segments with `MP4SplitSinkSettings`. The muxer starts a new file on a key frame after the configured duration, so each segment is independently playable:

```
var splitSettings = new MP4SplitSinkSettings("capture_%05d.mp4")
{
    SplitDuration = TimeSpan.FromMinutes(5),  // new file every 5 minutes
    SplitMaxFiles = 12                        // keep the latest 12 files (0 = unlimited)
};

var sink = new MP4SinkBlock(splitSettings);
```

The `%05d` placeholder in the location pattern is replaced with the zero-padded segment index.

## Adding a Live Preview

You can record and preview simultaneously by teeing the encoded video, sending one branch to the recorder and decoding the other for display. This mirrors the [UDP RAW Capture Demo](https://github.com/visioforge/.Net-SDK-s-samples/tree/master/Media%20Blocks%20SDK/WPF/CSharp/UDP%20RAW%20Capture%20Demo):

```
using VisioForge.Core.MediaBlocks.Special;
using VisioForge.Core.MediaBlocks.VideoRendering;

var tee = new TeeBlock(2, MediaBlockPadMediaType.Video);

var recorder = new MP4SinkBlock(new MP4SinkSettings("output.mp4"));
var recVideoInput = (recorder as IMediaBlockDynamicInputs).CreateNewInput(MediaBlockPadMediaType.Video);

// Preview branch: decode for display only.
var decoder = new DecodeBinBlock(renderVideo: true, renderAudio: false, renderSubtitle: false);
var renderer = new VideoRendererBlock(pipeline, VideoView1); // VideoView1 is your UI control

pipeline.Connect(source.VideoOutput, tee.Input);
pipeline.Connect(tee.Outputs[0], recVideoInput);             // recording branch (no decode)
pipeline.Connect(tee.Outputs[1], decoder.Input);             // preview branch
pipeline.Connect(decoder.VideoOutput, renderer.Input);
```

The recording branch stays a pure passthrough; only the preview branch decodes.

## Key Considerations

- **Container/codec compatibility**: MP4 stores H.264, H.265, and AAC well — exactly what a typical UDP MPEG-TS broadcast feed carries. MPEG-TS (`.ts`) is more permissive and more resilient to a recording that ends abruptly (power loss), because it has no trailing index to write.
- **Audio is opt-in**: if you leave `AudioEnabled = false`, `AudioOutput` stays `null` and the recording is video-only. Always guard `if (source.AudioOutput != null)` before connecting audio.
- **Multicast vs unicast**: a multicast group address in the URL (`224.0.0.0`–`239.255.255.255`) is joined automatically; a unicast bind (`0.0.0.0` or a specific local IP) just listens. Make sure your firewall allows inbound UDP on the chosen port.
- **Packet loss**: UDP does not retransmit. On a lossy network you may see brief artifacts in the recording; the muxer keeps running and the file stays valid.
- **Resource cleanup**: dispose the recorder (and therefore the pipeline) when done, and call `VisioForgeX.DestroySDK()` once on application exit.

## Troubleshooting

- **Empty or zero-duration file** — usually means no data arrived. Confirm the sender targets the same port, check the firewall, and verify the URL is the local listening endpoint (`0.0.0.0:port`), not the sender's address.
- **`Could not multiplex` / muxer errors** — indicates buffers without a PTS. Use `Mode = Auto` or `Mode = MPEGTS` so the source inserts the timestamp-inferring parsers; do not bypass them for a container feed.
- **Silent recording** — `AudioEnabled` was left `false`, or the stream carries no audio, so `AudioOutput` was `null` and no audio pad was connected.
- **Multicast stream not received** — the network may not route the group to your host. Confirm the multicast address and that the switch/router forwards it; test with a unicast bind first.
- **Wrong codec assumed in RTP/Raw mode** — `Auto`/`MPEGTS` modes detect the codec from the container. Only `RTP` and `Raw` modes require you to set `VideoCodec` explicitly.

## Frequently Asked Questions

### Can I record a UDP MPEG-TS stream without re-encoding in C#?

Yes. `UDPRAWSourceBlock` exposes the already-encoded H.264/H.265 video and AAC audio on its output pads. Connect them straight to an `MP4SinkBlock` or `MPEGTSSinkBlock` and the streams are remuxed to disk with no decode or encode step.

### What is the difference between remuxing and transcoding?

Remuxing (stream copy/passthrough) copies the compressed packets into a new container unchanged — fast, lossless, low CPU. Transcoding decodes the stream and re-encodes it, which lets you change codec, resolution, or bitrate but costs CPU and reduces quality. To simply save a UDP feed, remuxing is the right choice.

### How do I record a multicast UDP stream?

Use a multicast group address in the URL, e.g. `udp://239.1.1.1:1234`. The source joins the group automatically. Make sure your network forwards the multicast group to the recording host and the firewall allows inbound UDP on the port.

### Which container should I record to — MP4 or MPEG-TS?

Use MP4 when you want a single, widely-compatible file for H.264/H.265 + AAC. Use MPEG-TS (`.ts`) when you need maximum codec flexibility or resilience to an abrupt stop, since TS has no trailing index that must be finalized.

### Does remuxing to MP4 keep the original video quality?

Yes. The encoded video and audio packets are copied byte-for-byte into the MP4 container, so the recording is identical in quality to the incoming stream. Quality only changes if you choose to transcode instead.

## What You Will Build

A video call between a .NET desktop application and a person in a web browser — a help desk agent and a customer, a kiosk and an operator, a lab instrument and a remote expert. Both sides see and hear each other with sub-second latency, and nothing runs between them: no media server, no cloud service, no browser plug-in.

```
graph LR;

```

Three blocks do the work:

| Block | Role in the call |
| --- | --- |
| `WebRTCSinkBlock` | Sends your camera and microphone to the browser. Runs the signalling server and serves the call page. |
| `WebRTCSourceBlock` | Receives the browser's camera and microphone, decoded, for a `VideoRendererBlock` and the speakers. |
| `EchoCancellationBlock` | Removes the caller's voice that your speakers play and your microphone picks up again, so the caller does not hear an echo. Also suppresses noise and levels the microphone. |

## When to Use It

- **One application, one caller at a time**, on the same network or across the internet with a TURN server.
- You want the call inside your own application — next to your controls, recordings or measurements — and the caller to need nothing but a link.
- You do not want to run or pay for a media server.

For one stream to many viewers use `WebRTCSinkBlock` alone ([Screen and Camera to Browsers](../webrtc-whip/)), and to publish through a media server use WHIP and WHEP ([WebRTC Player (WHEP)](../webrtc-whep-player/)).

## Prerequisites

- Windows x64 (the platform the demo and the tests run on), .NET 10.
- Media Blocks SDK .NET 2026.11.26 or later, with the `VisioForge.CrossPlatform.Core.Windows.x64` and `VisioForge.CrossPlatform.Core.Windows.Adds.x64` packages. The `.Adds` package carries the WebRTC and echo cancellation plugins.
- A camera and a microphone, and Chrome, Edge, Firefox or Safari for the caller.

Check `WebRTCSinkBlock.IsAvailable()`, `WebRTCSourceBlock.IsAvailable()` and `EchoCancellationBlock.IsAvailable()` before you build the pipeline: each returns `false` when the `.Adds` package is missing.

## How the Two Sides Find Each Other

The browser and the application meet on the signalling server that `WebRTCSinkBlock` runs (WebSocket, port 8443 by default):

1. `WebRTCSinkBlock` registers as a **producer**: anyone on the server can ask for its stream.
2. `WebRTCSourceBlock`, with neither `ProducerPeerId` nor `ConnectToFirstProducer` set, registers as a consumer that **waits to be called**.
3. The call page registers as a producer and a listener. It asks for the application's stream (one WebRTC session) and calls the waiting `WebRTCSourceBlock` with its own camera and microphone (a second session).

Each direction is its own WebRTC session, so the two can use different codecs and bitrates, and the sink adapts its bitrate to the caller's network.

## The Pipeline

```
var pipeline = new MediaBlocksPipeline();

// Your side: camera and microphone to the browser. The sink serves the call page from wwwroot.
var sink = new WebRTCSinkBlock(new WebRTCSinkSettings
{
    SignallingServerHost = "127.0.0.1",
    SignallingServerPort = 8443,
    WebServerDirectory = Path.Combine(AppContext.BaseDirectory, "wwwroot"),
    WebServerAddress = "http://127.0.0.1:8080/",
});

var camera = new SystemVideoSourceBlock(new VideoCaptureDeviceSourceSettings(videoDevice));
var microphone = new SystemAudioSourceBlock(audioDevice.CreateSourceSettings());
var echoCancellation = new EchoCancellationBlock(new EchoCancellationSettings());

pipeline.Connect(camera.Output, sink.CreateNewInput(MediaBlockPadMediaType.Video));
pipeline.Connect(microphone.Output, echoCancellation.Input);
pipeline.Connect(echoCancellation.Output, sink.CreateNewInput(MediaBlockPadMediaType.Audio));

// The caller's side: the renderers wait for the call. The caller's voice passes the echo canceller
// on its way to the speakers, so the canceller knows what to remove from the microphone.
var remoteVideo = new VideoRendererBlock(pipeline, RemoteView) { IsSync = false };
pipeline.AddBlock(remoteVideo);
pipeline.Connect(echoCancellation.PlaybackOutput, new AudioRendererBlock().Input);

await pipeline.StartAsync();

// The source joins the sink's signalling server once it runs, and waits for the call page to call it.
var source = new WebRTCSourceBlock(new WebRTCSourceSettings { SignallingServer = "ws://127.0.0.1:8443" });
source.VideoOutput.OnDemandConnect = true;
source.AudioOutput.OnDemandConnect = true;

pipeline.AddBlockLive(source);
pipeline.ConnectLive(source.VideoOutput, remoteVideo.Input);
pipeline.ConnectLive(source.AudioOutput, echoCancellation.PlaybackInput);
pipeline.SyncBlockStateLive(source);
```

Why the source is added after `StartAsync`: its signalling client connects as soon as the source starts, and the sink's server is listening only once the pipeline runs. `OnDemandConnect = true` keeps the source's outputs open for `ConnectLive`.

`WebRTCSinkBlock.ConsumerAdded` and `ConsumerRemoved` tell you when the caller joins and leaves. When the caller hangs up and calls again, the same `WebRTCSourceBlock` takes the new call through the same outputs; nothing needs to be rebuilt.

## The Call Page

The demo's `wwwroot/index.html` is a single file of plain JavaScript, no libraries. The parts that matter:

```
// Register as a producer (to call the application) and a listener (to see it arrive).
// callPage marks call pages: the 'list' and 'peerStatusChanged' handlers skip producers whose
// meta has it, so two open pages never take each other for the application.
send({ type: 'setPeerStatus', roles: ['producer', 'listener'], meta: { callPage: true } });
send({ type: 'list' });          // the application's sink: receive its stream
send({ type: 'listConsumers' }); // the application's waiting source: call it

// list → startSession with the sink's peer ID: the sink sends an offer, the page answers.
// listConsumers → startSession with the source's peer ID: the server replies with
// startSession, and the page offers its camera and microphone.
```

The page opens one `RTCPeerConnection` for each session and routes every `peer` message by its `sessionId`. Copy the file as is, or use it as a reference for your own page.

## Mute and Camera Off

- **Mute**: put a `VolumeBlock` before the echo canceller and set `Mute = true`. The call keeps its audio track; the caller hears silence.
- **Camera off**: put a `VideoBalanceBlock` after the camera and set `Settings.Contrast = 0`, `Settings.Saturation = 0` and `Settings.Brightness = -1`. The caller sees a black picture, and the video track stays, so turning the camera back on needs no new negotiation.

Both take effect while the call runs. In the browser, `track.enabled = false` does the same on the caller's side.

## Limits

- **HTTPS outside localhost.** Browsers give a page the camera and microphone only on `https://` or on `localhost`/`127.0.0.1`, and the sink's built-in web server is `http://` only. For a caller on another computer, host the call page on your own `https://` site, leave `WebServerDirectory` empty, and give the sink `SignallingServerCertificate` and `SignallingServerKey` so the page reaches the signalling server over `wss://`. Set `SignallingServerHost` to `0.0.0.0` so the page can connect at all, and, since the server then takes `wss://` only, set `WebRTCSourceSettings.SignallingServer` to `wss://127.0.0.1:<port>` (the source does not check the server's certificate, so the site's host name in it does not matter here).
- **TURN across the internet.** On one local network the two sides connect directly. Behind NAT or a firewall, run a TURN server (for example coturn) and set it in `WebRTCSinkSettings.TurnServers` and `WebRTCSourceSettings.TurnServers` (`turn://user:password@host:3478`) and in the page's `iceServers` (`{ urls: 'turn:host:3478', username, credential }`). STUN alone (`StunServer`, Google's server by default) is not enough for symmetric NAT.
- **One caller at a time.** `WebRTCSourceBlock` takes one call at a time: a 1:1 call, not a conference. A second caller who calls during a call receives your picture but is not shown, even after the first caller hangs up.
- **Echo cancellation needs both paths.** With `PlaybackInput` left unconnected the canceller has nothing to compare against and removes nothing. Both paths run at 48 kHz; the canceller resamples.
- **Windows is the tested platform.** The same plugins ship in `VisioForge.CrossPlatform.Core.macOS.Adds`; on other platforms check `IsAvailable()`.

## Frequently Asked Questions

### Do I need a media server or a cloud service for a WebRTC call from .NET?

No. `WebRTCSinkBlock` runs the signalling server inside your application and serves the call page, and the media flows directly between the application and the browser. Only a TURN server is needed when the two sides cannot reach each other directly.

### How does the browser call the .NET application?

The call page registers on the application's signalling server as a producer and starts a session with the waiting `WebRTCSourceBlock`. The server tells the page to send its offer, and the source answers. A second session in the other direction carries the application's camera and microphone.

### Why does the caller hear an echo, and how is it removed?

The caller's voice comes out of your speakers and goes back into your microphone. `EchoCancellationBlock` listens to what the speakers play (its playback path) and subtracts it from the microphone (its main path). Connect both paths; headphones avoid the echo altogether.

### Which codecs are used?

The browser and the blocks negotiate them per session: VP8, H.264, VP9, H.265 or AV1 for video, whichever both sides support, and Opus for audio. The video the source outputs is decoded, in the size and frame rate the browser sends.

### Can the call run across the internet?

Yes, with the call page on an `https://` site, the signalling server on `wss://`, and a TURN server for callers behind NAT. See [Limits](#limits).

        _pipeline.OnError += (_, args) => Dispatcher.InvokeAsync(() => Title = args.Message);

        // Video is always asked for; audio only when the stream has it: the server refuses a track it does not send
        var audio = cbAudio.IsChecked == true;
        var source = new WHEPSourceBlock(new WHEPSourceSettings
        {
            Location = edURL.Text.Trim(),
            AudioEnabled = audio,
        });

        // IsSync = false: play each frame the moment it arrives, the lowest latency, at the cost of lip sync
        var video = new VideoRendererBlock(_pipeline, VideoView1) { IsSync = false };
        _pipeline.Connect(source.VideoOutput, video.Input);

        if (audio)
        {
            var speakers = new AudioRendererBlock { IsSync = false };
            _pipeline.Connect(source.AudioOutput, speakers.Input);
        }

        var started = await _pipeline.StartAsync();
        if (!started) await StopAsync();

        btStart.IsEnabled = !started;
        cbAudio.IsEnabled = !started;
        btStop.IsEnabled = started;
        IsEnabled = true;
    }

    private async Task StopAsync()
    {
        await _pipeline.StopAsync();
        await _pipeline.DisposeAsync();
        _pipeline = null;
    }

    private async void btStop_Click(object sender, RoutedEventArgs e)
    {
        IsEnabled = false;
        await StopAsync();
        btStop.IsEnabled = false;
        btStart.IsEnabled = true;
        cbAudio.IsEnabled = true;
        IsEnabled = true;
    }

    private async void Window_Closing(object sender, CancelEventArgs e)
    {
        if (IsEnabled && _pipeline == null)
        {
            VisioForgeX.DestroySDK();
            return;
        }

        e.Cancel = true; // busy, or still playing: stop first
        if (!IsEnabled) return; // loading, starting or stopping: close again after
        IsEnabled = false;

        if (_pipeline != null) await StopAsync();

        IsEnabled = true;
        await Dispatcher.InvokeAsync(Close); // not Close(): WPF throws inside Closing
    }
}
```

What each part does:

- **`VisioForgeX.InitSDKAsync`** loads the SDK and its GStreamer runtime once, when the window opens. **`WHEPSourceBlock.IsAvailable()`** then tells whether the WHEP client is there: without the `Adds` package it is not, the title bar says so, and **Start** stays disabled.
- **`WHEPSourceBlock`** does the WebRTC work: it posts the WHEP request to `Location`, connects over ICE, and decodes the video and audio it receives. Its `VideoOutput` and `AudioOutput` carry decoded frames and samples.
- **`AudioEnabled`** decides whether the block asks the server for audio. A stream with no audio track must be played with it off: MediaMTX refuses a session that asks for a track the stream does not have, and `OnError` reports `codecs not supported by client`. `AudioEnabled` defaults to `true`, so the sample sets it from the **Audio** check box, off by default.
- **`IsSync = false`** on both renderers shows each frame and plays each sample the moment it arrives, instead of holding it for its time on the pipeline clock. That keeps the latency at its lowest, at the cost of exact lip sync.
- **`OnError`** is raised on a GStreamer thread, so the handler marshals to the UI thread with `Dispatcher.InvokeAsync`. It reports errors the server sends after `StartAsync` returned too: a path with nothing published on it, or a refused track.
- **`StopAsync` and `DisposeAsync`** end the WebRTC session and release the pipeline. **`Window_Closing`** cancels a close while the player plays, stops the pipeline, and closes again; on that second pass the SDK is released with `VisioForgeX.DestroySDK()`. A close while the SDK loads, starts or stops is ignored: close the window again once it is enabled.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| The title bar says `No WHEP source`, **Start** is disabled | The `VisioForge.CrossPlatform.Core.Windows.Adds.x64` package is not referenced. Add it. |
| The title bar says `codecs not supported by client` | The player asked for a track the stream does not have, usually audio. Turn **Audio** off for a video-only stream. |
| The title bar shows an HTTP error such as `404` | Nothing is published on that path, or the URL is wrong. On MediaMTX the URL ends with `/<stream name>/whep`. |
| **Start** succeeds but the video stays black | The WebRTC media does not get through: allow the app through Windows Defender Firewall, and on MediaMTX the server's WebRTC UDP port (8189). Across networks, set `StunServer` or `TurnServer` in `WHEPSourceSettings`. |
| Audio and video drift apart | `IsSync = false` plays each stream as it arrives. Set `IsSync = true` on both renderers for lip sync, at the cost of a higher latency. |

## Frequently Asked Questions

### Which servers does it play from?

Any server that publishes over WHEP: MediaMTX, Janus, Cloudflare Stream and others. For servers that need a token, set `AuthToken` in `WHEPSourceSettings`; it is sent as `Authorization: Bearer`.

`WHEPSourceBlock` runs on Windows, macOS and Linux with the platform's `Adds` package (on Linux also with the distribution's `gstreamer1.0-plugins-bad` and `gstreamer1.0-nice`), and on iOS with `VisioForge.CrossPlatform.Core.iOS` 2026.11.23 or later. Yes. Put a `TeeBlock` after the source's `VideoOutput`, connect one output to the renderer and the other to an encoder and a file sink. `MediaBlocksPipeline.StopAsync` finalizes the file.

With `WHIPSinkBlock`: see [Screen or Camera to a Browser over WebRTC](../webrtc-whip/). To serve RTSP cameras to browsers over WHEP without a media server, see [RTSP Cameras in a Browser with WHEP](../rtsp-cameras-in-browser-whep/).

## What You Will Build

Two ways to put a live screen, an application window or a camera in front of people who only have a web browser, both with sub-second latency:

1. **Straight to the browsers, no server.** `WebRTCSinkBlock` turns your .NET application into a WebRTC server: it serves the viewer page, runs the signalling, and sends every viewer their own WebRTC stream. Nothing to install next to the application.
2. **Through a media server, with WHIP.** `WHIPSinkBlock` publishes one stream to a WebRTC media server — MediaMTX, Janus, Cloudflare Stream — over WHIP (WebRTC-HTTP Ingestion Protocol). The server then delivers it to any number of viewers, on the internet as well.

```
graph LR;
    src["Screen, window or camera<br/>+ microphone"] --> app;
    subgraph app ["Your .NET application"]
        WebRTCSinkBlock;
        WHIPSinkBlock;
    end
    WebRTCSinkBlock -- "WebRTC, VP8 + Opus" --> b1["Browsers on your network"];
    WHIPSinkBlock -- "WHIP: H.264 + Opus" --> server["Media server<br/>MediaMTX, Janus"];
    server -- "WebRTC (WHEP)" --> b2["Browsers anywhere"];
```

Which one to use:

|  | `WebRTCSinkBlock` | `WHIPSinkBlock` |
| --- | --- | --- |
| Extra software | none | a WebRTC media server |
| Encoding | VP8 and Opus, one encoder per viewer, with per-viewer congestion control | H.264 and Opus, encoded once in your pipeline |
| CPU per extra viewer | one more VP8 encoder | none: the server forwards the stream |
| Viewer page | served by the block, about 100 lines of JavaScript | the server's own player, or any WHEP player |
| Platforms | Windows, macOS, Linux, iOS | Windows, macOS, Linux, iOS |
| Typical use | screen sharing and camera views for a few viewers on a local network | publishing to many viewers, or across the internet |

## Part 1: Straight to Browsers with WebRTCSinkBlock

### How a viewer connects

`WebRTCSinkBlock` runs two servers inside your process: a web server for the viewer page and a WebSocket signalling server. The page asks the signalling server for the stream, the block sends a WebRTC offer, and the browser answers. From then on the video goes over the viewer's own WebRTC connection.

```
sequenceDiagram
    participant Browser
    participant Web as Web server (WebRTCSinkBlock)
    participant Sig as Signalling server (WebRTCSinkBlock)
    Browser->>Web: GET /?signalling=8443
    Web-->>Browser: index.html
    Browser->>Sig: WebSocket: register as a listener, list producers
    Browser->>Sig: start a session with the producer
    Sig-->>Browser: SDP offer (VP8, Opus)
    Browser->>Sig: SDP answer, ICE candidates
    Sig-->>Browser: ICE candidates
    Note over Browser,Sig: ConsumerAdded is raised
    Note over Browser,Sig: the screen or camera plays over the viewer's own WebRTC connection
```

Every viewer gets its own encoder and its own congestion control, so a viewer on a slow Wi-Fi link gets a lower bitrate without lowering the quality for the others.

### The complete program

The console program below sends the primary screen — or, with `camera` on the command line, the first camera — and the first microphone to every browser that opens `http://localhost:8090/?signalling=8443`.

```
using System;
using System.IO;
using System.Threading.Tasks;

using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.Types;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.Sources;

// 127.0.0.1 serves this computer only; "0.0.0.0" serves viewers on other computers too.
const string Host = "127.0.0.1";
const int WebPort = 8090;
const int SignallingPort = 8443;

await VisioForgeX.InitSDKAsync();

MediaBlocksPipeline? pipeline = null;

try
{
    if (!WebRTCSinkBlock.IsAvailable())
    {
        Console.WriteLine("WebRTCSinkBlock is not available: add the VisioForge.CrossPlatform.Core.Windows.Adds.x64 package.");
        return;
    }

    pipeline = new MediaBlocksPipeline();
    pipeline.OnError += (s, e) => Console.WriteLine(e.Message);

    // The primary screen by default, the first camera with "camera" on the command line.
    MediaBlock video;
    if (args.Length > 0 && args[0] == "camera")
    {
        var cameras = await DeviceEnumerator.Shared.VideoSourcesAsync();
        if (cameras.Length == 0)
        {
            Console.WriteLine("No camera found.");
            return;
        }

        video = new SystemVideoSourceBlock(new VideoCaptureDeviceSourceSettings(cameras[0]));
    }
    else
    {
        video = new ScreenSourceBlock(new ScreenCaptureD3D11SourceSettings { FrameRate = new VideoFrameRate(30) });
    }

    // Its own signalling server, plus a web server for the viewer page in wwwroot.
    var webrtc = new WebRTCSinkBlock(new WebRTCSinkSettings
    {
        SignallingServerHost = Host,
        SignallingServerPort = SignallingPort,
        WebServerDirectory = Path.Combine(AppContext.BaseDirectory, "wwwroot"),
        WebServerAddress = $"http://{Host}:{WebPort}/"
    });
    webrtc.ConsumerAdded += (s, e) => Console.WriteLine($"Viewer connected: {e.PeerId}");
    webrtc.ConsumerRemoved += (s, e) => Console.WriteLine($"Viewer left: {e.PeerId}");

    // Raw video: the sink encodes it to VP8 for each viewer.
    pipeline.Connect(video.Output, webrtc.CreateNewInput(MediaBlockPadMediaType.Video));

    // The first microphone, if there is one: encoded to Opus for each viewer.
    var microphones = await DeviceEnumerator.Shared.AudioSourcesAsync();
    if (microphones.Length > 0)
    {
        var microphone = new SystemAudioSourceBlock(microphones[0].CreateSourceSettings());
        pipeline.Connect(microphone.Output, webrtc.CreateNewInput(MediaBlockPadMediaType.Audio));
    }

    if (await pipeline.StartAsync())
    {
        Console.WriteLine($"Open http://localhost:{WebPort}/?signalling={SignallingPort} in a browser. Press Enter to stop.");
        Console.ReadLine();
    }
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}
finally
{
    if (pipeline != null)
    {
        await pipeline.StopAsync();
        await pipeline.DisposeAsync();
    }

    VisioForgeX.DestroySDK();
}
```

Copy the viewer page to the output folder with the build — add this to the `.csproj`:

```
<ItemGroup>
  <Content Include="wwwroot\**" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>
```

What each part does:

- **`ScreenSourceBlock` with `ScreenCaptureD3D11SourceSettings`** captures the primary monitor through Direct3D 11 at its native resolution. `FrameRate` defaults to 10; 30 makes mouse movement and scrolling smooth. `MonitorIndex` picks another monitor.
- **`SystemVideoSourceBlock`** opens a camera. `new VideoCaptureDeviceSourceSettings(device)` picks its HD format when it has one; set `Format` to choose another.
- **`WebRTCSinkBlock.CreateNewInput`** creates one input per call. Raw video and audio are encoded by the block for each viewer, video to VP8 and audio to Opus. Video already encoded to VP8 (with `VPXEncoderBlock`) is sent as it is, without an encoder per viewer.
- **`WebServerDirectory`** turns on the block's web server and points it at the folder with `index.html`. Leave it `null` to serve the page yourself (see [Serving the page from your own web server](#serving-the-page-from-your-own-web-server)).
- **`SignallingServerHost`** and the host in **`WebServerAddress`** decide who can connect: `127.0.0.1` accepts this computer only, `0.0.0.0` every network interface.
- **`ConsumerAdded` / `ConsumerRemoved`** report each viewer that connects and leaves. They are raised on a GStreamer thread: in a UI application marshal to the UI thread, as the demo does with `Dispatcher.Invoke`. `ConsumerRemoved` is not raised for viewers still connected when the pipeline stops; their sessions end with it.
- **`try` / `finally`** reports what went wrong and always stops and disposes the pipeline and calls `VisioForgeX.DestroySDK()`. When `StartAsync` returns `false`, the reason is in the `OnError` messages — a port already in use is the common one.

### The viewer page

The page speaks the signalling protocol of the GStreamer `webrtcsink` element: JSON messages over a WebSocket. Save it as `wwwroot/index.html`. It is the WebRTC Browser Streamer Demo's page: it plays the first stream the server announces, retries when the application is not running yet, and starts muted so the browser plays it without a click.

```
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>VisioForge WebRTC Viewer</title>
    <link rel="icon" href="data:,">
    <style>
        body { margin: 0; background: #111; color: #ddd; font-family: system-ui, sans-serif; display: flex; flex-direction: column; align-items: center; }
        video { width: 100%; max-width: 1280px; max-height: 80vh; background: #000; margin-top: 16px; }
        #bar { margin: 12px 16px; display: flex; gap: 12px; align-items: center; }
        button { padding: 6px 14px; }
    </style>
</head>
<body>
    <video id="video" autoplay playsinline muted></video>
    <div id="bar">
        <button id="unmute">Unmute</button>
        <span id="status">Connecting...</span>
    </div>

    <script>
        // Signalling port of WebRTCSinkBlock: ?signalling=8443 in the page URL.
        const port = new URLSearchParams(location.search).get('signalling') || '8443';
        const video = document.getElementById('video');
        const status = document.getElementById('status');
        let ws, pc, sessionId;

        document.getElementById('unmute').onclick = () => { video.muted = false; };

        function send(msg) { ws.send(JSON.stringify(msg)); }

        function connect() {
            // An https:// page needs wss://: set SignallingServerCertificate and SignallingServerKey.
            ws = new WebSocket(`${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.hostname}:${port}`);
            ws.onopen = () => send({ type: 'setPeerStatus', roles: ['listener'], meta: null });
            ws.onclose = () => { reset(); status.textContent = 'Disconnected, retrying...'; setTimeout(connect, 2000); };
            ws.onmessage = e => onMessage(e.data).catch(err => fail('Error: ' + err));
        }

        function startSession(peerId) {
            if (sessionId === undefined) {
                sessionId = null;
                send({ type: 'startSession', peerId });
            }
        }

        async function onMessage(data) {
            const msg = JSON.parse(data);
            switch (msg.type) {
                case 'welcome':
                    send({ type: 'list' });
                    break;
                case 'list':
                    if (msg.producers.length > 0) startSession(msg.producers[0].id);
                    else status.textContent = 'Waiting for the stream...';
                    break;
                case 'peerStatusChanged':
                    if (msg.roles.includes('producer')) startSession(msg.peerId);
                    break;
                case 'sessionStarted':
                    sessionId = msg.sessionId;
                    break;
                case 'peer':
                    await onPeer(msg);
                    break;
                case 'endSession':
                    reset();
                    status.textContent = 'Stream ended, waiting...';
                    listLater();
                    break;
                case 'error':
                    fail('Error: ' + msg.details);
                    break;
            }
        }

        async function onPeer(msg) {
            if (msg.sdp && msg.sdp.type === 'offer') {
                // Mirror the sink's StunServer and TurnServers here when it is given them.
                if (pc) { pc.close(); video.srcObject = null; }
                pc = new RTCPeerConnection({ iceServers: [{ urls: 'stun:stun.l.google.com:19302' }] });
                const conn = pc;
                pc.onconnectionstatechange = () => {
                    if (conn === pc && conn.connectionState === 'failed') {
                        video.srcObject = null;
                        fail('Connection lost');
                    }
                };
                pc.ontrack = e => { video.srcObject = e.streams[0] || new MediaStream([e.track]); status.textContent = 'Playing'; };
                pc.onicecandidate = e => {
                    if (e.candidate) send({ type: 'peer', sessionId, ice: { candidate: e.candidate.candidate, sdpMLineIndex: e.candidate.sdpMLineIndex } });
                };
                await pc.setRemoteDescription(msg.sdp);
                const answer = await pc.createAnswer();
                await pc.setLocalDescription(answer);
                send({ type: 'peer', sessionId, sdp: { type: 'answer', sdp: answer.sdp } });
            } else if (msg.ice && pc) {
                await pc.addIceCandidate({ candidate: msg.ice.candidate, sdpMLineIndex: msg.ice.sdpMLineIndex });
            }
        }

        // An error while a stream plays (a stale message, a rejected candidate) leaves it alone;
        // otherwise the session is ended and the producer list asked for again.
        function fail(text) {
            if (video.srcObject) {
                status.textContent = text;
                return;
            }

            if (sessionId) send({ type: 'endSession', sessionId });
            reset();
            status.textContent = text + ', retrying...';
            listLater();
        }

        // Asks for the producer list again after a pause, so a failing session does not retry in a tight loop.
        function listLater() {
            const socket = ws;
            setTimeout(() => { if (ws === socket && ws.readyState === WebSocket.OPEN) send({ type: 'list' }); }, 2000);
        }

        function reset() {
            if (pc) pc.close();
            pc = undefined;
            sessionId = undefined;
            video.srcObject = null;
        }

        connect();
    </script>
</body>
</html>
```

The exchange, step by step:

1. **Register as a listener.** The page opens a WebSocket to the signalling port and sends `setPeerStatus` with the `listener` role, then asks for the `list` of producers. Your application is the producer.
2. **Start a session.** The page sends `startSession` with the producer's ID; a producer that appears later is announced with `peerStatusChanged`, so the page can be opened before the application starts.
3. **Answer the offer.** The block sends the SDP offer in a `peer` message; the page creates an `RTCPeerConnection`, answers, and both sides exchange ICE candidates in further `peer` messages.
4. **Play.** `ontrack` hands the stream to the `<video>` element. The status shows `Playing`; **Unmute** turns the sound on, because browsers play a muted video without a click and an unmuted one only after it.
5. **Recover.** When the connection fails or the application stops, the page resets and asks for the list again, so it reconnects by itself when the stream comes back.

### Share one window instead of the whole screen

Set `WindowHandle` to capture a single application window through Windows Graphics Capture. The window is captured even when other windows cover it, and the rest of the desktop stays private:

```
var screen = new ScreenCaptureD3D11SourceSettings
{
    FrameRate = new VideoFrameRate(30),
    WindowHandle = windowHandle // HWND of the window to share, for example Process.MainWindowHandle
};

var video = new ScreenSourceBlock(screen);
```

The stream takes the window's size when the capture starts. A minimized window gives no frames until it is restored.

### Serving the page from your own web server

The block's web server is optional. With `WebServerDirectory` left `null`, only the signalling server runs; put `index.html` in your own site (ASP.NET Core, IIS, nginx) and pass the signalling port in the query string. The page connects to `ws://<the page's host>:<port>`, or `wss://` when the page itself is on `https://`, so the signalling server must be reachable on the same host name as the page.

### A viewer page on an HTTPS site

A browser blocks a `ws://` connection from an `https://` page. Give the signalling server your site's certificate and private key as PEM files and it speaks `wss://`:

```
var webrtcSink = new WebRTCSinkBlock(new WebRTCSinkSettings
{
    SignallingServerHost = "0.0.0.0",
    SignallingServerPort = 8443,
    SignallingServerCertificate = @"C:\certs\fullchain.pem",
    SignallingServerKey = @"C:\certs\privkey.pem"
});
```

The certificate must be valid for the host name in the page's address, and the key must not be encrypted. `Build` fails, with an `OnError` message, when only one of the two is set, a file cannot be read, the key is not the certificate's (checked on .NET 5 and later), or `WebServerDirectory` is set as well. The block's own web server serves `http://` only, so put an `https://` page on your own web server (IIS, nginx, ASP.NET Core) and leave `WebServerDirectory` `null`.

### Viewers on other computers

1. Set `Host` to `"0.0.0.0"`, so both servers listen on every network interface.
2. Allow the web port and the signalling port (8090 and 8443 here) through Windows Defender Firewall, and the application itself for the WebRTC media, which uses UDP ports chosen at run time.
3. Open `http://<this computer's address>:8090/?signalling=8443` on the other computer.

Receiving WebRTC needs no HTTPS, so plain `http://` works on a local network: we opened the demo's page by the computer's network address, which the browser treats as not secure, and the camera played. `WebRTCSinkSettings` has no authentication setting: anyone who can reach the two ports can watch. Keep `127.0.0.1` when the stream should not leave the computer, and use WHIP with a media server that checks tokens when it must reach the internet.

## Part 2: Publish to a Media Server with WHIPSinkBlock

### The pipeline

WHIP takes encoded H.264 video and Opus audio. The pipeline encodes once; the media server forwards the stream to every viewer.

```
graph LR;
    ScreenSourceBlock -- "raw video" --> H264EncoderBlock;
    SystemAudioSourceBlock -- "raw audio" --> OPUSEncoderBlock;
    H264EncoderBlock -- H.264 --> WHIPSinkBlock;
    OPUSEncoderBlock -- Opus --> WHIPSinkBlock;
    WHIPSinkBlock -- "WHIP (HTTP + WebRTC)" --> MediaMTX;
```

### The complete program

The console program publishes the primary screen and the first microphone to `http://<server>:8889/screen/whip`, MediaMTX's WHIP endpoint for a stream named `screen`. Pass another endpoint on the command line. The screen is captured with `ScreenCaptureD3D11SourceSettings`, so this program builds for Windows; on macOS use `ScreenCaptureMacOSSourceSettings`, on Linux `ScreenCaptureXDisplaySourceSettings`, or a camera, as the Avalonia demo does.

```
using System;
using System.Threading.Tasks;

using VisioForge.Core;
using VisioForge.Core.MediaBlocks;
using VisioForge.Core.MediaBlocks.AudioEncoders;
using VisioForge.Core.MediaBlocks.Sinks;
using VisioForge.Core.MediaBlocks.Sources;
using VisioForge.Core.MediaBlocks.VideoEncoders;
using VisioForge.Core.Types;
using VisioForge.Core.Types.X.AudioEncoders;
using VisioForge.Core.Types.X.Sinks;
using VisioForge.Core.Types.X.Sources;
using VisioForge.Core.Types.X.VideoEncoders;

// The media server's WHIP endpoint; MediaMTX takes http://<server>:8889/<stream name>/whip.
var whipUrl = args.Length > 0 ? args[0] : "http://192.168.1.10:8889/screen/whip";

await VisioForgeX.InitSDKAsync();

MediaBlocksPipeline? pipeline = null;

try
{
    if (!WHIPSinkBlock.IsAvailable())
    {
        Console.WriteLine("WHIPSinkBlock is not available: add the VisioForge.CrossPlatform.Core.*.Adds package for this platform.");
        return;
    }

    pipeline = new MediaBlocksPipeline();
    pipeline.OnError += (s, e) => Console.WriteLine(e.Message);

    var screen = new ScreenSourceBlock(new ScreenCaptureD3D11SourceSettings { FrameRate = new VideoFrameRate(30) });

    // WHIP carries H.264 video and Opus audio: encode once here, the server serves every viewer.
    var h264 = new H264EncoderBlock(new OpenH264EncoderSettings());
    var whip = new WHIPSinkBlock(new WHIPSinkSettings { Location = whipUrl });

    pipeline.Connect(screen.Output, h264.Input);
    pipeline.Connect(h264.Output, whip.CreateNewInput(MediaBlockPadMediaType.Video));

    var microphones = await DeviceEnumerator.Shared.AudioSourcesAsync();
    if (microphones.Length > 0)
    {
        var microphone = new SystemAudioSourceBlock(microphones[0].CreateSourceSettings());
        var opus = new OPUSEncoderBlock(new OPUSEncoderSettings());
        pipeline.Connect(microphone.Output, opus.Input);
        pipeline.Connect(opus.Output, whip.CreateNewInput(MediaBlockPadMediaType.Audio));
    }

    if (await pipeline.StartAsync())
    {
        Console.WriteLine($"Publishing to {whipUrl}. Press Enter to stop.");
        Console.ReadLine();
    }
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}
finally
{
    if (pipeline != null)
    {
        await pipeline.StopAsync();
        await pipeline.DisposeAsync();
    }

    VisioForgeX.DestroySDK();
}
```

What each part does:

- **`H264EncoderBlock` with `OpenH264EncoderSettings`** encodes in software, on every Windows computer, in the Constrained Baseline profile that every browser decodes. On a computer with an NVIDIA, AMD or Intel GPU, a hardware encoder's settings (`NVENCH264EncoderSettings`, `AMFH264EncoderSettings`, `QSVH264EncoderSettings`) take the encoding off the CPU.
- **`OPUSEncoderBlock`** encodes the microphone to Opus, the audio codec of WebRTC.
- **`WHIPSinkBlock.CreateNewInput`** creates the video and the audio input. The block adds the RTP packaging itself, so the encoders connect to it directly. Audio is optional: without a microphone the stream is video only.
- **`WHIPSinkSettings.Location`** is the WHIP endpoint. On `StartAsync` the block posts its SDP offer there, the server answers, and the media flows over WebRTC. On stop the block deletes the session on the server.

### Watching the stream

MediaMTX serves its own player for every stream at `http://<server>:8889/<stream name>/` — here `http://<server>:8889/screen/`. Any WHEP player can read it too, from `http://<server>:8889/screen/whep`, including the SDK's own [`WHEPSourceBlock`](../../Sources/#whep-source-block).

### Authentication, STUN and TURN

```
var whip = new WHIPSinkBlock(new WHIPSinkSettings
{
    Location = "https://media.example.com/live/whip",
    AuthToken = "secret-token",                     // sent as "Authorization: Bearer secret-token"
    StunServer = "stun://stun.l.google.com:19302",
    TurnServer = "turn://user:password@turn.example.com:3478"
});
```

- **`AuthToken`** — the bearer token of services that require one (Cloudflare Stream, a Janus or MediaMTX server with authentication).
- **`StunServer` / `TurnServer`** — the publisher's side of NAT traversal. Unset, the block uses no STUN server, which is enough when the application and the server are on the same network. `UseLinkHeaders` (on by default) also takes the ICE servers the WHIP server announces in its `Link` headers.
- **`IceTransportPolicy = WHIPIceTransportPolicy.Relay`** sends everything through the TURN server, for networks that block direct UDP.
- **`Timeout`** (15 seconds by default) bounds every WHIP HTTP request, including the session's `DELETE` on stop.

## Both from One Capture

One capture can feed both outputs at the same time: viewers on the local network get the stream straight from the application, and the media server gets the WHIP stream for everyone else. `TeeBlock` splits the video:

```
var tee = new TeeBlock(2, MediaBlockPadMediaType.Video);
pipeline.Connect(screen.Output, tee.Input);

// Local viewers: raw video, encoded per viewer to VP8.
pipeline.Connect(tee.Outputs[0], webrtc.CreateNewInput(MediaBlockPadMediaType.Video));

// The media server: H.264, encoded once.
pipeline.Connect(tee.Outputs[1], h264.Input);
pipeline.Connect(h264.Output, whip.CreateNewInput(MediaBlockPadMediaType.Video));
```

`TeeBlock` is in `VisioForge.Core.MediaBlocks.Special`. The two outputs start and stop together: a WHIP server that cannot be reached fails the start of the whole pipeline. Put them in two pipelines when the local stream must keep running without the server.

## Limits to Know Before Shipping

### Platforms

`WebRTCSinkBlock` runs on Windows, macOS and Linux with the platform's `Adds` package, and on iOS with `VisioForge.CrossPlatform.Core.iOS` 2026.11.23 or later: an older `Core.iOS` has the plugin without its fixes, so the sink starts, but `StopAsync` can hang when a viewer leaves during its negotiation. `WHIPSinkBlock` runs on the same platforms with the same packages. On Linux both also need the distribution's `gstreamer1.0-plugins-bad` and `gstreamer1.0-nice`. Check `IsAvailable()` at startup, as both programs do.

### Codecs

`WebRTCSinkBlock` sends VP8 video and Opus audio, which every current browser plays. It takes raw video and audio, or VP8 and Opus already encoded; it does not take H.264. `WHIPSinkBlock` takes H.264 and Opus only.

### Latency

In our test on one Windows computer, a change in a 320×240 picture at 30 frames per second reached a viewer's decoded frame 55 to 60 ms after it left the source (median 58 ms), before the viewer's playout delay. With a window's capture and the browser's playout and display added, the screenshot at the start of this guide shows about 0.15 seconds.

### CPU and resolution

`WebRTCSinkBlock` runs a software VP8 encoder per viewer. In our tests on one Windows computer, a 1080p camera and a 1902×1131 window played at 30 frames per second, while a whole 3840×2160 monitor reached about 20 frames per second in the browser. For a 4K screen, scale the video down before the sink with `VideoResizeBlock` (namespace `VisioForge.Core.MediaBlocks.VideoProcessing`):

```
var resize = new VideoResizeBlock(1920, 1080);
pipeline.Connect(screen.Output, resize.Input);
pipeline.Connect(resize.Output, webrtc.CreateNewInput(MediaBlockPadMediaType.Video));
```

For more than a handful of viewers, publish once with WHIP and let the media server serve them.

### Bitrate

`StartBitrate` (2 Mbit/s) is where each viewer starts; congestion control (`CongestionControl`, Google Congestion Control by default) raises it up to `MaxBitrate` (8 Mbit/s) while the network keeps up and lowers it when it does not. Raise `MaxBitrate` for sharp text on a large screen; set `CongestionControl = WebRTCSinkCongestionControl.Disabled` to hold every viewer at `StartBitrate`.

### Ports

The defaults are 8443 for signalling and 8080 for the web server. When a port is taken, `StartAsync` returns `false` and `OnError` says which port. The programs in this guide use 8090 for the page.

### NAT, STUN and TURN

On a local network no STUN server is needed. For viewers behind other networks, set `StunServer` and `TurnServers` in `WebRTCSinkSettings` (`StunServer` defaults to `stun://stun.l.google.com:19302`) and the same servers in the page's `iceServers` list. Across the internet, WHIP to a media server with a public address is usually the simpler route.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `IsAvailable()` returns `false` | The platform's `Adds` package is not referenced (on iOS, `VisioForge.CrossPlatform.Core.iOS` is missing or the SDK is older than 2026.11.23), or on Linux `gstreamer1.0-plugins-bad` and `gstreamer1.0-nice` are missing. |
| `StartAsync` returns `false`, `OnError` says the web server cannot listen | The web port is in use by another program. Choose another `WebServerAddress` port, or stop the other program. |
| The page says `Disconnected, retrying...` | The signalling server is not reachable: the application is not running, the `?signalling=` port is wrong, or the firewall blocks it. |
| The page says `Waiting for the stream...` | The page reached the signalling server, but the pipeline is not playing yet. Check `StartAsync` and the `OnError` messages. |
| The page says `Playing` but there is no sound | The video starts muted. Press **Unmute**. |
| A viewer on another computer stays at `Connection lost` | The WebRTC media is blocked: allow the application through the firewall, or set STUN/TURN on both sides. |
| A Direct3D 11 screen capture never plays in the browser, the page keeps reconnecting | Media Blocks SDK .NET 2026.11.20 or earlier. Update to 2026.11.21 or later. |
| The screen plays at a low frame rate | A 4K screen is encoded per viewer in software. Scale it to 1080p with `VideoResizeBlock`, or publish with WHIP. |
| WHIP: `StartAsync` returns `false` or `OnError` reports an HTTP error | The endpoint is wrong, the server is down, or it refused the token. Open the same URL's player page in a browser to check the server. |
| WHIP: the stream reaches the server but stays black or `ICE failed` | UDP between the application and the server is blocked. Allow the server's WebRTC UDP port (8189 on MediaMTX), or set a TURN server with `IceTransportPolicy = Relay`. |

## Frequently Asked Questions

### Do I need a media server to show my screen in a browser?

No. `WebRTCSinkBlock` serves the page, runs the signalling and streams to each browser from your process. A media server earns its place when there are many viewers or they are on the internet; then publish to it with `WHIPSinkBlock`.

### Why VP8 for browsers and H.264 for WHIP?

`WebRTCSinkBlock` encodes per viewer and uses VP8, which every browser decodes and which the block can adapt to each viewer's bandwidth. WHIP servers such as MediaMTX forward one stream to all viewers without re-encoding, so the stream must already be in a codec they accept; H.264 is the one every server and browser takes.

### How many viewers can WebRTCSinkBlock serve?

Each viewer costs one VP8 encoder. A 1080p stream runs a handful of viewers on a desktop CPU; at 4K the first viewer is already the limit. For more viewers, publish once with WHIP.

### Can I add audio?

Yes. Connect a raw audio source to `CreateNewInput(MediaBlockPadMediaType.Audio)` of `WebRTCSinkBlock` — it encodes Opus per viewer — or an `OPUSEncoderBlock` output to the audio input of `WHIPSinkBlock`.

### Does it work on macOS and Linux?

Both do, and both run on iOS too. To serve cameras without a viewer page of your own, use [`WHEPServerSinkBlock`](../rtsp-cameras-in-browser-whep/).

### Can a browser play the WHIP stream without the media server's page?

Yes. The server exposes the stream over WHEP, and a page with about 20 lines of JavaScript plays it — the player in [RTSP Cameras in a Browser with WHEP](../rtsp-cameras-in-browser-whep/#the-browser-side-a-minimal-whep-player) works against MediaMTX's `/whep` URL.

## Introduction

Media Blocks SDK for .NET is a pipeline-based multimedia framework that lets you build custom video and audio processing workflows in C#. Instead of using a fixed API with predefined behavior, you create a pipeline by connecting typed blocks — sources, encoders, effects, renderers, and sinks — to construct exactly the processing chain your application needs.

The SDK runs on Windows, macOS, Linux, Android, and iOS. It powers use cases that the higher-level Video Capture SDK and Media Player SDK cannot cover: multi-source compositing, custom transcoding pipelines, simultaneous encoding to multiple formats, real-time video effects chains, and integration with hardware like Blackmagic Decklink or industrial cameras.

## When to Use Media Blocks

Media Blocks SDK is the right choice when you need full control over the multimedia pipeline. Use it instead of (or alongside) the other VisioForge SDKs when:

| Scenario | Recommended SDK |
| --- | --- |
| Simple webcam recording to MP4 | [Video Capture SDK](../videocapture/) |
| Play a video file with standard controls | [Media Player SDK](../mediaplayer/) |
| Custom pipeline: source → effects → encode → multiple outputs | **Media Blocks SDK** |
| Live video compositing from multiple sources | **Media Blocks SDK** |
| Transcoding / format conversion with custom processing | **Media Blocks SDK** |
| RTSP recording with post-processing (overlay, resize, re-encode) | **Media Blocks SDK** |
| Cross-platform Avalonia or MAUI media app | **Media Blocks SDK** |
| Integration with Decklink, GenICam, or NVIDIA hardware | **Media Blocks SDK** |
