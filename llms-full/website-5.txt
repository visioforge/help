## Architecture Deep Dive

### Video Capture SDK .NET Architecture

The Video Capture SDK ships two engines, each with its own class. VideoCaptureCore wraps DirectShow and Media Foundation on Windows, giving native access to every capture device the OS exposes, and reads IP cameras through FFmpeg, VLC, LAV or low-latency RTSP back-ends. VideoCaptureCoreX is built on GStreamer and runs on Windows, macOS, Linux, iOS and Android. Moving between the two engines means rewriting the capture code.

-   ▶Native Windows capture via DirectShow and Media Foundation filter graphs
-   ▶Cross-platform GStreamer engine for Windows, macOS, Linux, iOS, and Android
-   ▶GPU-accelerated preview via Direct3D / OpenGL renderers
-   ▶Event-driven architecture with .NET async/await support
-   ▶In-process capture pipeline; only the FFMPEG\_EXE outputs launch an external vfffmpeg.exe (vfffmpeg64.exe in 64-bit processes)
-   ▶Typed output classes for recording and streaming configuration

### LibVLCSharp Architecture

LibVLCSharp is the official .NET binding for libvlc, the core engine behind the VLC media player. It provides a managed wrapper around VLC's C API, giving access to VLC's extensive media playback capabilities. While primarily designed for playback, it can open capture devices using VLC's media resource locator syntax (dshow://, screen://, v4l2://).

-   ▶Managed .NET wrapper around libvlc C API via P/Invoke
-   ▶Monolithic VLC engine handles all media operations
-   ▶Capture devices accessed via URL-style media resource locators
-   ▶Recording configured via sout (stream output) string chains
-   ▶Playback-first design — capture is a secondary use case
-   ▶Cross-platform via platform-specific VLC native libraries

### Key Architectural Differences

| Aspect | Video Capture SDK | LibVLCSharp |
| --- | --- | --- |

| Effects Pipeline | Built-in CPU + GPU effect chain during capture | VLC filter strings in the sout chain |

### LGPL Compliance Considerations

LibVLCSharp and libvlc are licensed under LGPL 2.1+. This means you can use them in commercial proprietary software as long as you comply with the LGPL terms. Key requirements include:

-   ⚠Static linking is restricted by LGPL relinking terms
-   ⚠You must provide the ability for users to replace the LGPL-licensed library with a modified version
-   ⚠You must include a copy of the LGPL license and prominently mention the use of libvlc
-   ⚠If you modify libvlc itself, you must release those modifications under LGPL
-   ⚠Videolabs sells a commercial license for the LibVLCSharp packages; LibVLC itself stays under its open-source license

While LGPL is more permissive than GPL, compliance still requires careful attention to linking and distribution requirements. Video Capture SDK itself is commercially licensed, but the open-source libraries it bundles, such as GStreamer, keep their own licenses; GStreamer is LGPL, so the same linking and distribution requirements apply to it.

### Example 4: RTSP IP Camera Surveillance with Detection

```csharp
using VisioForge.Core.VideoCapture;
using VisioForge.Core.Types;
using VisioForge.Core.Types.Output;
using VisioForge.Core.Types.VideoCapture;
using VisioForge.Core.Types.VideoProcessing;

var cameras = new List<VideoCaptureCore>();
var cameraUrls = new[]
{
    "rtsp://192.168.1.101/stream",
    "rtsp://192.168.1.102/stream",
    "rtsp://192.168.1.103/stream",
    "rtsp://192.168.1.104/stream"
};

foreach (var url in cameraUrls)
{
    var cam = new VideoCaptureCore();
    cam.IP_Camera_Source = new IPCameraSourceSettings
    {
        URL = new Uri(url),
        Type = IPSourceEngine.Auto_FFMPEG
    };

    // Motion detection
    cam.Motion_Detection = new MotionDetectionSettings { Enabled = true };
    cam.OnMotion += (s, e) =>
    {
        Console.WriteLine($"Motion on {url}");
    };

    // Barcode detection
    cam.Barcode_Reader_Enabled = true;
    cam.OnBarcodeDetected += (s, e) =>
    {
        Console.WriteLine($"Barcode: {e.Value}");
    };

    // Segmented recording (split file every hour)
    cam.Output_Format = new MP4Output();
    cam.Output_Filename = $"cam_{cameras.Count}.mp4";
    cam.SeparateCapture_Enabled = true;
    cam.SeparateCapture_TimeThreshold = TimeSpan.FromHours(1);
    cam.Mode = VideoCaptureMode.IPCapture;

    cameras.Add(cam);
}

foreach (var cam in cameras)
    await cam.StartAsync();
```

## Architecture Deep Dive

### Video Capture SDK .NET Architecture

The Video Capture SDK uses a pipeline-based design. You configure source, processing stages, and outputs declaratively. The engine assembles the internal filter graph automatically, handling threading, synchronization, and buffer management. VideoCaptureCore wraps DirectShow and Media Foundation on Windows; VideoCaptureCoreX is built on GStreamer and runs across platforms.

-   ▶Declarative pipeline configuration: set properties, call StartAsync()
-   ▶Dual engine: native OS capture APIs on Windows, GStreamer across platforms
-   ▶GPU-accelerated preview via Direct3D / OpenGL renderers
-   ▶Event-driven architecture with .NET async/await support
-   ▶Single-process model with automatic thread management
-   ▶Multi-output from one pipeline: record + stream + snapshot simultaneously

### MFormats SDK Architecture

MFormats uses a frame-based grab-process-output model built on COM objects. You create an MFReader or MFLive to grab frames, process each MFFrame, and push it to MFWriter, MFRenderer, or MFPreview receivers. This gives fine-grained per-frame control but requires you to write the capture loop, manage threading, and handle frame timing manually.

-   ▶Frame-based loop: grab frame from MFReader, process, push to MFWriter
-   ▶COM-based architecture with .NET interop wrappers
-   ▶Manual threading and frame timing management required
-   ▶Per-frame control allows custom routing logic
-   ▶Separate objects for each pipeline stage (Reader, Live, Writer, Renderer, Preview)
-   ▶No playlist object; Medialooks places playlist automation in MPlatform

## Frequently Asked Questions

How is MFormats licensed?

Medialooks lists no MFormats prices on its own site. ComponentSource sells company licenses for up to four developers with 12 months of updates and support: Pro €4,413.97, Expert €7,196.69 and Ultimate €11,226.84, with renewals at about half the first-year price; plugins are extra. The Video Capture SDK offers perpetual licenses that continue working indefinitely after purchase.

Does the Video Capture SDK support AJA or Bluefish444 SDI cards?

Currently, the Video Capture SDK supports Blackmagic DeckLink SDI cards but does not support AJA or Bluefish444 hardware. If your project requires multi-vendor SDI support across AJA, Bluefish, and Deltacast alongside Blackmagic, MFormats is the better choice for that specific requirement.

Can the Video Capture SDK run on macOS and Linux?

Yes. The Video Capture SDK supports Windows, macOS (Apple Silicon and Intel), Linux x64, Linux ARM64, Android, and iOS. MFormats is Windows-only due to its COM-based architecture. Medialooks also offers xMedia SDK, a separate C++ library with C# and Python wrappers that Medialooks says runs on Windows, Linux, and macOS with the same API; it is not on NuGet and its price is on request. This page compares MFormats.

How do the pricing models compare for a team of 5 developers over 3 years?

MFormats company licenses at ComponentSource cover up to four developers, so five developers need more than one license or a quote from Medialooks; one Pro license over 3 years is €8,827.95 (€4,413.97 plus two €2,206.99 renewals). The Video Capture SDK Lifetime·Team license costs €900–1,800 as a one-time perpetual purchase covering the purchasing organization's developers at one location in one city.

Does MFormats have built-in motion detection or face detection?

No. MFormats does not include built-in detection features. You would need to integrate third-party libraries for motion detection, face detection, or barcode scanning. The Video Capture SDK includes all of these as built-in features with event-driven callbacks.

Which SDK is better for broadcast playout applications?

MFormats gives frame-level control over playback to multi-vendor SDI devices, but it has no playlist object: Medialooks places playlist automation in MPlatform, and the Character Generator and HTML5 overlays are separately licensed MFormats plugins. The Video Capture SDK has no playout scheduling either, so for broadcast playout automation look at Medialooks MPlatform.

Can I migrate from MFormats to the Video Capture SDK?

Yes, but the programming models are different. MFormats uses a frame-based grab-process-output loop, while the Video Capture SDK uses a declarative pipeline. Migration typically involves replacing the manual frame loop with pipeline configuration and event handlers. Most teams find the SDK code is significantly shorter and easier to maintain.

## Frequently Asked Questions

Does TVideoGrabber support RTMP streaming to YouTube or Twitch?

Yes, through an add-on. TVideoGrabber streams over RTMP, SRT, HLS, and its own RTSP server with the Multipurpose Encoder, a separate €950 product; the base license covers ASF network streaming. The Video Capture SDK includes RTMP, RTSP, SRT, HLS, and NDI streaming in its Premium edition, with no add-ons.

Can TVideoGrabber record to multiple files simultaneously?

Only through the Multipurpose Encoder add-on, which can send several outputs at once. The base component records one file at a time and can roll over to a new file. In the Video Capture SDK, the cross-platform engine adds outputs with Outputs\_Add, and the Windows engine records and streams at the same time.

How much does TVideoGrabber cost compared to the SDK?

TVideoGrabber is €700 per developer. The RTSP/RTMP/HTTP/ONVIF Source Filter and the Multipurpose Encoder are €950 each and the NDI Filters €400; Datastead's Suite of all four products costs €2,100 per developer. The Video Capture SDK Premium costs €500 per year for one developer or €1,800 for a Lifetime·Team license covering all developers at one location.

Does the Video Capture SDK support ONVIF PTZ camera control like TVideoGrabber?

Yes. Both products support ONVIF PTZ camera control including pan, tilt, zoom, and preset positions. This is one area where the two products are comparable in functionality.

Can I use TVideoGrabber on macOS or Linux?

No. TVideoGrabber is a Windows-only component based on DirectShow, which is a Windows-specific technology. It does not run on macOS, Linux, Android, or iOS. The Video Capture SDK supports all five platforms through its cross-platform engine.

Does the Video Capture SDK support OCR?

Yes. The SDK's VisioForge.DotNet.Core.AI package includes OcrBlock, based on PaddleOCR, which you register as a video processing block on VideoCaptureCoreX; OCR is a Premium feature. OCR does not appear in the TVideoGrabber documentation, so there you would pair it with a third-party library such as Tesseract.

Can I switch from TVideoGrabber to the Video Capture SDK?

Yes. The API styles differ: TVideoGrabber uses property-based configuration, while the SDK uses async events and managed objects. The migration effort depends on the size of the project, and you gain cross-platform support, GPU effects, and a single team license.

## Architecture Deep Dive

### Video Capture SDK .NET Architecture

The Video Capture SDK uses a dual-engine design. The primary engine (VideoCaptureCore) wraps DirectShow and Media Foundation on Windows, giving native access to every capture device exposed by the OS. A secondary cross-platform engine (VideoCaptureCoreX) is built on GStreamer and supports Windows, macOS, Linux, Android, and iOS. Each engine has its own class and members, so moving between them means porting code.

-   ▶Native Windows capture via DirectShow and Media Foundation filter graphs
-   ▶Cross-platform GStreamer engine for macOS, Linux, Android, and iOS
-   ▶GPU-accelerated preview via Direct3D / OpenGL renderers
-   ▶Event-driven architecture with .NET async/await support
-   ▶Dual-engine design: VideoCaptureCore (Windows) and VideoCaptureCoreX (cross-platform)

### Viscomsoft Video Capture SDK Architecture

Viscomsoft Video Capture SDK is a basic ActiveX/COM component that wraps DirectShow for webcam access on Windows. It provides a simple API for capturing video from USB webcams and recording to MP4 or WMV files. The architecture is limited to a single DirectShow filter graph with no embedded codec engine or cross-platform support.

-   ▶ActiveX/COM wrapper around DirectShow filter graph
-   ▶Limited to USB webcam devices exposed via DirectShow
-   ▶No embedded codec engine — relies on system-installed codecs
-   ▶No cross-platform support — Windows only
-   ▶Basic .NET interop via COM wrapper — not a native .NET API

Can Viscomsoft record in 4K resolution?

Does Viscomsoft have motion detection or face detection?

Can I migrate from Viscomsoft to the Video Capture SDK?

## Architecture Deep Dive

### Video Edit SDK .NET — Dual-Engine Architecture

The SDK ships two rendering back-ends selectable per project: a native DirectShow/Media Foundation pipeline for Windows-specific scenarios and a cross-platform GStreamer-based pipeline (VideoEditCoreX). Each engine has its own class (VideoEditCore and VideoEditCoreX) and its own members, so moving between them means porting code.

-   +Native pipeline (VideoEditCore) adds network streaming, virtual camera, and DeckLink output on Windows
-   +GStreamer pipeline (VideoEditCoreX) enables cross-platform builds targeting macOS, Linux, iOS, and Android
-   +Automatic codec negotiation eliminates manual format-string construction
-   +Choose the engine per project: VideoEditCore for Windows-only features, VideoEditCoreX for cross-platform builds

### FFmpeg .NET Wrappers — CLI Process Model

FFmpeg wrappers launch the ffmpeg binary as a child process, passing arguments via command-line strings. The wrapper parses stdout/stderr for progress reporting and exit codes for error handling. This architecture is simple to understand but introduces inherent limitations.

-   ~No in-process memory sharing — all data flows through the filesystem or pipes
-   ~Progress reporting depends on parsing FFmpeg console output (fragile)
-   ~Error messages are raw FFmpeg stderr, requiring manual interpretation
-   ~Each operation spawns a new process, adding startup overhead for batch workloads

### Key Architectural Differences

| Aspect | Video Edit SDK | FFmpeg Wrappers |
| --- | --- | --- |
| Execution Model | In-process native library | Out-of-process CLI invocation |
| Memory Access | Direct frame buffer access | Filesystem or pipe-based I/O |
| Error Handling | .NET events with error descriptions | Exit code + stderr parsing |
| Threading | Managed thread pool integration | Separate OS process per job |
| State Management | Stateful timeline/session objects | Stateless per-invocation |
| Extensibility | Custom effects and processing blocks | Custom FFmpeg builds or filtergraph scripts |

## Frequently Asked Questions

Can I use Video Edit SDK .NET and FFmpeg together in the same project?

Yes. VideoEditCoreX is built on GStreamer, not FFmpeg, so there is no license overlap or dependency conflict if you add an FFmpeg wrapper to the same project. Both libraries coexist independently — the SDK handles your editing pipeline while an FFmpeg wrapper covers any supplementary tasks (exotic formats, CLI-only filters).

Does FFmpeg's GPL license affect my commercial application?

It depends on your FFmpeg build configuration. If your FFmpeg binary includes GPL-licensed components (like libx264 or libx265), the entire binary is GPL, which requires you to distribute your application's source code or use dynamic linking with LGPL-only components. The Video Edit SDK's commercial license avoids these concerns entirely.

Which option is faster for batch transcoding?

For pure transcoding throughput, performance is comparable because both rely on the same underlying hardware and battle-tested codec implementations (x264, x265, NVENC, QSV, VA-API). VideoEditCoreX is built on GStreamer and routes encoding through these codecs natively, while FFmpeg wrappers shell out to the FFmpeg binary — so raw codec speed is similar. The Video Edit SDK adds slight overhead for its managed API layer. FFmpeg wrappers have per-process startup overhead. For GPU-accelerated encoding, the SDK can pick a hardware encoder without manual flags.

Can FFmpeg wrappers provide real-time video preview?

No. FFmpeg is a batch processing tool — it reads input, processes it, and writes output. There is no mechanism for interactive scrubbing, frame-accurate seeking, or real-time playback within an FFmpeg wrapper. If you need preview, you need either the Video Edit SDK or a separate media player component.

What happens if FFmpeg updates and breaks my wrapper's argument parsing?

This is a known risk with CLI wrappers. FFmpeg occasionally changes argument syntax, deprecates flags, or modifies output formats between major versions. Wrapper libraries must update to match, and there can be a lag. The Video Edit SDK avoids this class of problem entirely: VideoEditCoreX is built on GStreamer rather than the FFmpeg binary, and the SDK exposes a stable managed .NET API instead of command-line strings, so updates are tested and shipped as stable NuGet packages.

How do I handle errors from FFmpeg wrappers?

FFmpeg wrappers typically expose the process exit code and stderr output. You must parse error messages yourself, as they are raw FFmpeg console text. Common patterns include regex matching on error strings and exit code mapping. The Video Edit SDK reports errors through OnError events with descriptions, making error handling more structured.

Is the Video Edit SDK trial sufficient for evaluating all features?

The trial is fully functional for 30 days. Depending on the SDK engine and output, it may display a watermark or an unregistered notice. It may be used for internal commercial development, but production use and distribution require a paid license. Annual includes 12 months of minor and major updates and email support; Lifetime·Team includes both for the product lifetime.

## Frequently Asked Questions

Can LibVLCSharp edit video?▼

LibVLCSharp documents media playback, seeking, audio output, and sout-based transcoding and streaming. Its official source does not document a built-in timeline, transition or multi-clip render API.

Can LibVLCSharp trim or convert a video file?▼

For one input, yes: LibVLC media options such as :start-time and :stop-time select a segment, and a :sout=#transcode{...}:std{...} chain re-encodes it to a file while the MediaPlayer runs. Each Media is processed on its own, so joining clips and transitions need another tool.

What does Video Edit SDK .NET provide?▼

Both engines, VideoEditCoreX (cross-platform) and VideoEditCore (Windows), can add video and audio clips with timeline positions, apply transitions and effects, preview a timeline, or render to a configured file output. VideoEditCoreX has 70+ GES transitions; VideoEditCore adds 100+ DES transitions, lossless cut and join, and file encryption.

Can I use Video Edit SDK .NET and LibVLCSharp in the same app?▼

Yes. They are independent libraries, so a product can play media with LibVLCSharp and edit and export with Video Edit SDK .NET. If you only need to show the edit before rendering, Video Edit SDK .NET previews its own timeline in a video view, so LibVLCSharp is not needed for that.

Which platforms do the two libraries support?▼

Video Edit SDK .NET runs its VideoEditCoreX engine on Windows, macOS, Linux, Android, and iOS, with UI bindings for WinForms, WPF, WinUI 3, .NET MAUI, Avalonia, and Uno Platform; the VideoEditCore engine is Windows-only. LibVLCSharp covers the same five platforms plus tvOS, and also supports Xamarin.

How much do Video Edit SDK .NET and LibVLCSharp cost?▼

LibVLCSharp is free under LGPL 2.1+ (LibVLC must stay replaceable), and Videolabs sells a commercial license for the LibVLCSharp packages at $800·year. Video Edit SDK .NET costs €250–500·year per developer or €900–1,800 one-time for a Lifetime·Team license covering all developers in the purchasing organization at one location in one city, with royalty-free distribution. The open-source libraries it bundles, such as GStreamer, stay under the LGPL.

When a project outgrows playback and needs a timeline, Video Edit SDK .NET is the editing counterpart: multi-track clips, transitions, timed text, effects and rendering through one C# API.
